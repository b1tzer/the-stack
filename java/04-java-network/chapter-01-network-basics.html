网络通信基础：程序如何跨越机器边界 ​

你在本地写了一个 userService.findById(1)，跑得飞快——0.1ms。把 UserService 拆成独立服务后，同一个调用变成了 40ms。你以为是代码慢了，加了缓存、优化了 SQL，降到 35ms。但你没想过的那个问题才是根本：你的机器在北京，另一台在东京，光缆里一个往返就是 80ms。拆服务之前，先看一下网络延迟在你眼里和在现实里到底差了多大。

1. 为什么程序需要网络 ​

1.1 从单机到分布式的范式转变 ​

在计算机发展的早期，一台大型机就能满足所有计算需求。程序之间的通信通过共享内存、管道、消息队列等本地机制完成。但随着业务规模增长，单机的算力、存储和可靠性都遇到了天花板。

我们来看一个典型的演进路径：

txt
单机应用
  → 数据库分离（应用服务器 + 数据库服务器）
    → 应用集群（多台应用服务器 + 负载均衡）
      → 微服务架构（数十个独立服务，各司其职）
        → 云原生与边缘计算（服务遍布全球）

每一次演进，都意味着程序之间需要跨越更远的物理距离、更多的网络节点来完成通信。网络不再是可选项，而是程序运行的基本前提。

1.2 网络成为基础设施 ​

今天，几乎没有一个有意义的程序是完全孤立运行的。一个简单的"用户下单"操作，背后可能涉及：

  • 前端调用 API 网关
  • 网关路由到订单服务
  • 订单服务调用库存服务、支付服务、通知服务
  • 每个服务访问各自的数据库
  • 异步消息发送到消息队列

这些服务可能分布在不同的机器、不同的机房、甚至不同的国家。网络就是连接这一切的"血管"。

对 Java 开发者而言，理解网络不是"加分项"，而是"基本功"。

1.3 分布式系统的代价 ​

网络不是免费的午餐。引入分布式后，你必须面对一系列单机时代不存在的问题：

问题单机分布式
延迟内存访问 ~100ns网络往返 ~0.5-100ms（差 5-6 个数量级）
可靠性硬件故障 = 整体停机部分节点故障，系统仍可运行
一致性共享内存，天然一致需要共识协议（Paxos/Raft）
安全性本地通信，无需加密网络窃听、中间人攻击
调试单进程栈追踪分布式链路追踪（Jaeger/Zipkin）

Jeff Dean 的经典延迟数字（2020 年数据）：

txt
L1 cache reference               0.5 ns
L2 cache reference               7   ns
Main memory reference            100 ns
Read 1 MB from memory            0.25 ms
Round trip within same datacenter 0.5 ms
Read 1 MB from SSD               1   ms
Disk seek                        10  ms
Read 1 MB from network           10  ms
Read 1 MB from disk              20  ms
Send packet CA→Netherlands→CA     150 ms

网络往返（0.5ms）比内存访问（100ns）慢 5000 倍。 这就是为什么分布式系统设计的核心挑战，本质上都是在与网络延迟和不可靠性做斗争。

2. 网络通信的本质 ​

2.1 本质：发送 bytes，接收 bytes ​

剥离所有协议、框架和抽象，网络通信做的事情只有一件：把一串字节从机器 A 的进程送到机器 B 的进程。

txt
机器 A 的进程                          机器 B 的进程
┌──────────────┐                     ┌──────────────┐
│  application │                     │  application │
│   buffer     │                     │   buffer     │
│ [0x48,0x65,  │  ──── 网络 ────▶     │ [0x48,0x65,  │
│  0x6C,0x6C,  │                     │  0x6C,0x6C,  │
│  0x6F]       │                     │  0x6F]       │
└──────────────┘                     └──────────────┘
        "Hello"                              "Hello"

不管上层用的是 HTTP、gRPC、WebSocket 还是自定义协议，最终落到网线/光纤上传输的都是字节。理解这一点，是理解所有网络编程的关键。

2.2 协议是对字节流的抽象封装 ​

既然本质是字节流，为什么我们需要 HTTP、RPC 这些协议？因为裸字节流解决不了以下问题：

问题裸字节流协议的作用
对方怎么知道一条消息结束了？不知道消息边界（长度字段、分隔符等）
数据格式是什么？不知道序列化格式（JSON、Protobuf 等）
请求和响应怎么对应？不知道请求 ID、会话标识
对方挂了怎么办？不知道超时、重试、心跳
大文件怎么传？一次性发送可能失败分块传输、流控

协议就是在字节流上附加的"约定"——通信双方共同遵守的规则。 不同的协议在不同的维度上做了取舍：

  • HTTP：简单、通用、无状态，适合请求-响应模式
  • WebSocket：全双工、持久连接，适合实时推送
  • gRPC：基于 HTTP/2 + Protobuf，高性能、强类型，适合微服务间通信
  • TCP：可靠、有序的字节流传输，是上述协议的共同基础

2.3 一个思想实验：如果让你设计协议 ​

假设你要在两个 Java 程序之间传输数据，你会怎么做？

最简单的方案：直接发字节。

java
// 发送方
outputStream.write("Hello".getBytes());

// 接收方
byte[] buf = new byte[1024];
int n = inputStream.read(buf);

但这立刻就会遇到问题：

  1. 消息边界：如果发送方连续发了 "Hello" 和 "World"，接收方可能一次读到 "HelloWorld"，也可能分两次读到 "Hel" 和 "loWorld"——你无法知道原始消息的边界在哪里。
  2. 编码："Hello".getBytes() 用的是什么字符集？UTF-8？GBK？如果不约定，接收方解码就会乱码。
  3. 大消息：如果消息有 10MB，一次 write() 可能成功，但接收方的 read() 可能只读到 4KB——你需要循环读取，但怎么知道什么时候读完了？
  4. 错误处理：如果网络断了，read() 会怎样？阻塞？抛异常？返回 -1？

这些问题，就是协议要解决的。每一层协议都是对下层的一次"标准化"——它规定了数据格式、交互时序和错误处理方式，让通信双方有共同的语言。

3. 网络分层模型 ​

3.1 OSI 七层 vs TCP/IP 四层 ​

网络通信涉及太多问题：物理信号、帧同步、路由寻址、可靠传输、数据格式……如果把所有逻辑写在一个巨大的模块里，复杂度会让人崩溃。分层是人类管理复杂度的经典手段——每一层只管自己的事，向上提供抽象，向下调用服务。

两种经典的分层模型：

txt
OSI 七层模型              TCP/IP 四层模型
┌───────────────┐        ┌───────────────┐
│  7. 应用层     │        │               │
├───────────────┤        │  应用层        │
│  6. 表示层     │        │  (HTTP/FTP/   │
├───────────────┤        │   DNS/SMTP)   │
│  5. 会话层     │        │               │
├───────────────┤        ├───────────────┤
│  4. 传输层     │        │  传输层        │
├───────────────┤        │  (TCP/UDP)    │
│  3. 网络层     │        ├───────────────┤
├───────────────┤        │  网际层        │
│  2. 数据链路层  │        │  (IP/ICMP)    │
├───────────────┤        ├───────────────┤
│  1. 物理层     │        │  网络接口层    │
└───────────────┘        └───────────────┘

TCP/IP 四层模型是互联网实际运行的模型。OSI 七层是理论参考模型。作为 Java 开发者，你主要关心的是应用层和传输层。

3.2 每层的职责与 Java 开发者的关注点 ​

层级职责典型协议/技术Java 开发者需要关心吗？
应用层定义业务数据格式和交互语义HTTP, gRPC, WebSocket, DNS, SMTP⭐⭐⭐ 核心战场
传输层提供端到端的可靠（或不可靠）传输TCP, UDP, QUIC⭐⭐ 需要理解原理
网际层路由寻址，把数据包从源送到目标IP, ICMP, ARP⭐ 了解即可
网络接口层物理信号传输，帧的封装与解析Ethernet, Wi-Fi, PPP几乎不关心

关键认知： Java 的 java.net.Socket 对应的是传输层（TCP），而 HttpURLConnection、Spring 的 RestTemplate 对应的是应用层（HTTP）。你写的每一行网络代码，都处于这个分层结构中的某个位置。

3.3 分层的代价 ​

分层不是没有代价的。每一层都要加自己的头部，带来了额外的开销：

txt
以太网帧有效载荷：1500 字节
- IP 头部：20 字节
- TCP 头部：20 字节
= 应用层可用：1460 字节

头部开销占比：40 / 1500 ≈ 2.7%

对于大文件传输，这个开销可以忽略。但对于大量小消息（如实时交易系统），头部开销可能成为瓶颈。这也是 QUIC 协议（HTTP/3 的基础）选择在 UDP 上重新设计的原因之一——它用更紧凑的头部格式来减少开销。

4. 数据如何从一台机器到另一台机器 ​

4.1 数据封装过程 ​

当你调用 socket.getOutputStream().write("Hello".getBytes()) 时，数据并不会直接飞到目标机器。它要经过层层封装，每一层加上自己的"信封"：

txt
应用层数据 (Application Data)
┌─────────────────────────────┐
│ "Hello" (5 bytes)           │
└─────────────────────────────┘
            │
            ▼  传输层加上 TCP 头（源端口、目标端口、序列号、校验和等）
┌─────────────────────────────────────────┐
│ TCP Header (20+ bytes) │ "Hello"        │
└─────────────────────────────────────────┘
            │
            ▼  网际层加上 IP 头（源IP、目标IP、TTL等）
┌──────────────────────────────────────────────────────┐
│ IP Header (20+ bytes) │ TCP Header │ "Hello"         │
└──────────────────────────────────────────────────────┘
            │
            ▼  链路层加上帧头帧尾（源MAC、目标MAC、CRC校验等）
┌──────────────────────────────────────────────────────────────────┐
│ Ethernet Header │ IP Header │ TCP Header │ "Hello" │ FCS Trailer│
└──────────────────────────────────────────────────────────────────┘

这个过程叫做封装（Encapsulation）。接收端收到数据后，执行相反的过程——解封装（Decapsulation），逐层剥离头部，最终把 "Hello" 交给目标应用。

4.2 一次完整的 HTTP 请求之旅 ​

以你在浏览器输入 http://example.com/index.html 为例：

txt
1. DNS 解析：example.com → 93.184.216.34
2. TCP 三次握手：与 93.184.216.34:80 建立连接
3. 发送 HTTP 请求：
   GET /index.html HTTP/1.1\r\n
   Host: example.com\r\n
   \r\n
4. 服务器处理请求，返回 HTTP 响应
5. 浏览器解析 HTML，渲染页面
6. TCP 四次挥手（或保持连接复用）

每一步都涉及数据的封装与解封装。 对 Java 开发者来说，你通常只关心第 3 步和第 4 步——但当网络出问题时（连接超时、数据丢失、性能瓶颈），理解底层过程能帮你快速定位问题。

4.3 MTU、MSS 与分片 ​

以太网帧的最大传输单元（MTU）通常是 1500 字节。如果一个 IP 数据包超过了 MTU，它会被分片（Fragmentation）：

txt
原始 IP 数据包 (3000 bytes payload)
┌──────────────────────────────────────────────┐
│              3000 bytes                       │
└──────────────────────────────────────────────┘
                    │
                    ▼ 分片
┌───────────────┐ ┌───────────────┐ ┌───────────────┐
│ Fragment 1    │ │ Fragment 2    │ │ Fragment 3    │
│ 1500 bytes    │ │ 1500 bytes    │ │ (剩余)        │
│ offset=0      │ │ offset=1480   │ │ offset=2960   │
│ MF=1          │ │ MF=1          │ │ MF=0          │
└───────────────┘ └───────────────┘ └───────────────┘

分片会降低网络效率（任何一个分片丢失，整个包要重传），所以 TCP 会通过 MSS（Maximum Segment Size） 协商来尽量避免分片。MSS 通常 = MTU - IP 头(20) - TCP 头(20) = 1460 字节。

4.4 IP 地址与端口号：通信的地址体系 ​

网络通信需要两个"地址"才能定位到具体的进程：

  • IP 地址：定位到哪台机器（网络层）
  • 端口号：定位到机器上的哪个进程（传输层）
txt
192.168.1.100:8080
│              │
│              └── 端口号（16 位，0-65535）
└───────────────── IP 地址（32 位 IPv4 / 128 位 IPv6）

端口号的分配有约定俗成的规则：

范围用途示例
0-1023知名端口（需要 root 权限）HTTP=80, HTTPS=443, SSH=22
1024-49151注册端口MySQL=3306, Redis=6379, Tomcat=8080
49152-65535动态/私有端口客户端临时端口

在 Java 中，ServerSocket 绑定的就是端口号：

java
// 监听 8080 端口
ServerSocket serverSocket = new ServerSocket(8080);

// 客户端连接 localhost:8080
Socket socket = new Socket("localhost", 8080);

5. UDP 与 DNS：连接建立之前的两个边界 ​

TCP 并不是所有网络通信的前提。UDP 在发送前不建立连接，DNS 则负责在 TCP 连接之前把主机名解析成地址。两者都容易被上层框架隐藏，却会直接影响延迟和故障判断。

5.1 UDP 提供数据报，不提供可靠传输 ​

UDP 把应用数据封装成独立数据报发送。它没有连接状态，也不保证数据到达、按序到达或只到达一次。Java 的传统 API 是 DatagramSocket 与 DatagramPacket，NIO API 是 DatagramChannel。

java
try (DatagramChannel channel = DatagramChannel.open()) {
    channel.configureBlocking(false);
    channel.bind(new InetSocketAddress(9000));
    ByteBuffer buffer = ByteBuffer.allocate(1500);
    SocketAddress sender = channel.receive(buffer);
    if (sender != null) {
        buffer.flip();
        // 按应用协议解析这一份数据报
    }
}

这段代码只说明数据报的接收边界，不提供业务协议。若需要确认、重传、顺序、流控或拥塞控制，必须在应用层补齐，或者改用提供这些语义的协议。典型选择如下：

需求UDP 的直接能力选择方向
音视频、遥测、DNS允许丢包，重视低延迟可直接使用 UDP 语义
RPC、文件传输、命令下发需要可靠和有序TCP、QUIC 或应用层确认机制
大量并发小消息数据报独立、无连接握手仍需自行设计重试、幂等和限流

UDP 报文还受 MTU、网络分片和中间设备策略影响。应用必须定义最大消息大小、解析失败策略和重复消息的幂等性；“收到了发送成功”不等于对端已经处理。

5.2 DNS 决定连接会去哪里 ​

访问 https://api.example.com/orders 时，通常先解析 api.example.com，再向得到的 IP 地址建立 TCP 连接。Java 可以显式查看解析结果：

java
import java.io.UncheckedIOException;

try {
    InetAddress[] addresses = InetAddress.getAllByName("api.example.com");
    for (InetAddress address : addresses) {
        System.out.println(address.getHostAddress());
    }
} catch (UnknownHostException ex) {
    throw new UncheckedIOException("无法解析 api.example.com", ex);
}

JDK 会对成功和失败结果进行缓存，具体策略受 JDK 版本、安全配置和网络环境影响。因此，一次 Java 查询返回同一地址不能证明 DNS 刚刚重新解析。排查时应同时观察应用侧结果、系统解析器和权威/递归 DNS：

text
应用 URL
  → JDK/系统 DNS 解析
  → IP 地址
  → TCP 建连
  → TLS 握手
  → HTTP 响应

这条链上的错误要分开判断：域名不存在通常是 DNS 问题；拿到地址后连接超时更可能是路由、端口或防火墙问题；TCP 成功但 TLS 失败则要检查证书链和主机名匹配。curl -w 的 time_namelookup、time_connect 和 time_appconnect 正好对应这些阶段，详见 HTTP 协议、Java 客户端与 TLS/HTTPS。

6. Java 网络编程全景 ​

6.1 Java 网络编程的演进路线 ​

Java 的网络编程经历了几个明显的阶段，每个阶段都是对前一阶段痛点的回应：

txt
JDK 1.0 (1996)          JDK 1.4 (2002)         JDK 7 (2011)
┌─────────────┐         ┌─────────────┐         ┌─────────────┐
│  java.net    │         │  java.nio    │         │  NIO.2      │
│  Socket      │         │  Channel     │         │  Asynchronous│
│  ServerSocket│         │  Buffer      │         │  Channel    │
│  BIO 阻塞 I/O│         │  Selector    │         │  FileSystem │
└─────────────┘         └─────────────┘         └─────────────┘
     ▲                       ▲                       ▲
     │                       │                       │
  一个连接               多路复用                异步非阻塞
  一个线程               少量线程                回调/CompletableFuture
阶段API模型优点缺点
BIOjava.net.Socket阻塞式 I/O简单直观一个连接占一个线程，万级连接就崩
NIOjava.nio.channels非阻塞 + 多路复用少量线程管理大量连接编程模型复杂，Buffer 操作反直觉
NIO.2java.nio.channels.AsynchronousChannel异步 I/O真正的异步，回调通知生态不如 NIO 成熟
Netty第三方框架Reactor 模式高性能、易用、生态丰富额外依赖，学习曲线

6.3 Java 网络编程的核心类库 ​

以下是 Java 网络编程中最常用的类，按层次组织：

层次核心类用途
传统 Socketjava.net.Socket, ServerSocket阻塞式 TCP 通信
传统 UDPjava.net.DatagramSocket, DatagramPacketUDP 数据报通信
URL/HTTPjava.net.URL, HttpURLConnectionHTTP 请求（已过时）
NIO 核心java.nio.channels.SocketChannel, ServerSocketChannel非阻塞 TCP 通信
NIO 多路复用java.nio.channels.Selector单线程管理多连接
NIO 缓冲区java.nio.ByteBuffer高效数据读写
NIO.2 异步java.nio.channels.AsynchronousSocketChannel异步非阻塞通信

java
// 传统 Socket（阻塞）
Socket socket = new Socket("localhost", 8080);
OutputStream out = socket.getOutputStream();
out.write("Hello".getBytes());

// NIO Channel（非阻塞）
SocketChannel channel = SocketChannel.open();
channel.connect(new InetSocketAddress("localhost", 8080));
ByteBuffer buffer = ByteBuffer.wrap("Hello".getBytes());
channel.write(buffer);

// HttpClient（JDK 11+，推荐）
HttpClient client = HttpClient.newHttpClient();
HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create("http://localhost:8080/api/hello"))
    .build();
HttpResponse<String> response = client.send(request,
    HttpResponse.BodyHandlers.ofString());

三种 API 的演进反映了 Java 网络编程的进化：从"一个连接一个线程"到"一个线程管理多个连接"，再到"声明式异步"。
