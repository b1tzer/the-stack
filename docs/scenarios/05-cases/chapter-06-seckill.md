# 秒杀

> 秒杀是库存扣减的一个极端变体，商品有限，但同一瞬间涌进来几十万请求。它的核心矛盾不是「怎么扣库存」，而是「怎么让几十万请求在到达数据库之前被层层拦截」。库存扣减只解决最后一步，前面的削峰才是秒杀的真正难点。

## 1. 秒杀难在哪

秒杀和平常下单的区别，不在业务逻辑，在流量形态。平常的请求是均匀的，秒杀的请求是在几秒内瞬间涌入，峰值可能是平常的几百上千倍。

数据库扛不住这个峰值。即使库存扣减逻辑写得再对，几十万请求同时打数据库，连接池先被占满，数据库直接不可用。所以秒杀要解决的第一件事，不是正确扣库存，而是让数据库只承受它能承受的那一小撮请求。

理解这一点，就能理解秒杀方案为什么是层层拦截的结构。每一层拦掉一批请求，到达数据库的请求量衰减到可控范围。

## 2. 层层拦截，把洪峰削平

第一层在前端。秒杀开始前按钮置灰，开始后点击一次就禁用，防住无意义的重复点击。

第二层在网关或限流层。对秒杀接口单独限流，超过阈值的请求直接拒绝，返回「活动太火爆」。限流的实现见 [限流器](../02-concurrency/chapter-02-rate-limiting.md)。

第三层是 Redis 预扣库存。请求过了限流，在 Redis 里用原子操作扣减库存，扣到不足就直接拒绝，根本不进数据库。这层拦住的是绝大部分「库存已空」的请求。预扣的具体实现（`DECRBY` 加回滚加异步落库）见 [库存扣减并发控制](./chapter-01-inventory-deduction.md) 的 Redis 预扣一节，这里不再贴代码。

第四层才是数据库。经过前面三层，真正到达数据库的请求，数量已经和库存量一个量级，数据库轻松承接。

## 3. Redis 预扣之后，异步落库

Redis 里扣减成功，不代表下单完成。下单要写订单表、扣库存表，这些还得落数据库。但落库不要求同步，扣减成功后发一条消息，由消费者异步完成订单创建和库存落库。

这引入了一个新问题，Redis 扣了库存，但异步落库还没完成，中间崩溃了怎么办。库存已经少了一份，数据库里还没记录。这就是 Redis 预扣的双份数据一致性问题，具体解法见 [库存扣减并发控制](./chapter-01-inventory-deduction.md) 里的 Redis 预扣一节。

秒杀场景对这个问题比普通库存更宽容，因为秒杀的商品本来就卖光了，Redis 里预扣的库存多扣少扣几件，影响的只是极少数用户的购买结果，不是资金安全。所以秒杀里 Redis 预扣加异步落库是标准做法，补偿机制做到「最终对账」这一层就够了。

## 4. 秒杀和普通库存扣减的区别

普通库存扣减，用数据库的悲观锁或乐观锁就够，因为并发没那么极端。秒杀不能用数据库锁，几十万请求在数据库行锁上排队，锁等待时间比业务本身还长。

所以秒杀几乎必然走 Redis 预扣这条路线，用 Redis 的单线程原子操作替代数据库行锁。这个选择不是「更优」，是「没有别的路」。数据库的锁在秒杀的量级下必崩。

同时秒杀对一致性的要求比普通库存低。普通库存多扣一件是事故，秒杀多扣几件几乎无感，因为它卖的就是「抢不到」这个结果。这个差异决定了秒杀可以更大胆地用异步，用最终一致换吞吐。

## 5. 结论

秒杀的核心是削峰，不是扣库存。前端、限流、Redis 预扣、数据库四层，每层拦掉一批，让洪峰衰减到数据库能承受的量。库存扣减的正确性靠 Redis 原子操作保证，一致性靠异步落库加对账兜底。把「洪峰」和「库存」这两件事分开想，秒杀方案就清晰了。
