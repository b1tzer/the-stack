# 版本控制与团队协作

一个人写项目可以随便改，但多人协作、或想回退到某个版本时，就需要版本控制。读完这一篇，你能正确配置 Unity 项目的 Git，理解 `.meta` 文件为什么必须提交，并避开多人协作的常见坑。

## 1. Unity 项目能用 Git 吗

能，而且推荐。Unity 项目本质上就是一堆文件：脚本（`.cs`）、场景（`.unity`）、资源（贴图、模型、音频）和配置。Git 管理这些文件，让你能记录历史、回退版本、多人协作。

但 Unity 项目有两个特殊性，处理不好会出问题，下面重点讲。

## 2. 哪些文件要忽略

Unity 项目里有些目录是**生成的临时文件**，不该提交。它们体积大、每次打开都会重新生成，提交只会浪费空间还制造冲突。

标准做法是加一个 `.gitignore`，忽略这些目录：

```txt
# Unity 生成的临时目录
[Ll]ibrary/
[Tt]emp/
[Oo]bj/
[Bb]uild/
[Bb]uilds/
[Ll]ogs/
[Uu]ser[Ss]ettings/

# IDE 相关
.idea/
.vs/
.vscode/
```

**提交的内容**应该是：`Assets/` 目录（脚本、资源、场景）、`Packages/`（包清单）、`ProjectSettings/`（项目设置）。`Library/` 是导入资源的缓存，克隆仓库后 Unity 会自动重新生成，不用提交。

## 3. `.meta` 文件必须提交

这是 Unity 项目最容易踩的坑。Unity 会为 `Assets/` 里的每个资源生成一个同名的 `.meta` 文件，存的是这个资源的**唯一标识符（GUID）** 和导入设置。

场景里的引用是靠 GUID 而不是文件名：

- 场景里一个物体引用某张贴图，存的是贴图的 GUID。
- 如果 `.meta` 文件没提交，别人拉取代码后 Unity 会为贴图重新生成一个**不同的 GUID**，导致场景里所有对该贴图的引用丢失（贴图变"丢失"状态）。

所以 **`.meta` 文件必须和资源一起提交**，`.gitignore` 里绝不能忽略 `*.meta`。

## 4. 场景文件的合并冲突

场景文件（`.unity`）是 YAML 格式，但**极难自动合并**。两个人都改了同一个场景，Git 合并时几乎必然冲突，而且手工解决场景冲突非常痛苦。

多人协作的应对策略：

- **拆分场景**：把不同功能放在不同场景，或用**预制体**拆分——每个人改自己的预制体，只在装配场景时合并。
- **分工避免同时改场景**：约定谁负责哪个场景，避免并行编辑同一个场景。
- **用预制体代替场景编辑**：把可复用的东西做成预制体（前面讲过），预制体作为独立文件提交，冲突概率远低于场景。

## 5. 一个最小 Git 配置流程

1. 初始化仓库：`git init`。
2. 添加 `.gitignore`（内容见第 2 节）。
3. 确保 `.meta` 文件被跟踪（不要忽略 `*.meta`）。
4. 提交 `Assets/`、`Packages/`、`ProjectSettings/` 和 `.gitignore`。
5. 推送到远程仓库（GitHub 等）。

首次提交后，验证一下：在另一台机器（或另一个目录）`git clone`，用 Unity Hub 打开，确认资源引用正常、没有"丢失"的资源。如果引用丢失，多半是 `.meta` 没提交。

## 6. 协作的常见坑

| 问题 | 原因 | 处理 |
| --- | --- | --- |
| 资源引用丢失（Missing） | `.meta` 文件没提交 | 补提交 `.meta`，或重新建立引用 |
| 场景合并冲突 | 两人同时改同一场景 | 拆预制体、分工避免并行改场景 |
| 仓库体积暴涨 | `Library/` 等临时目录被提交 | 加 `.gitignore` 并从仓库移除 |
| 换机器后打不开 | 项目版本不一致 | 团队统一 Unity 版本（用 Hub 锁定） |
