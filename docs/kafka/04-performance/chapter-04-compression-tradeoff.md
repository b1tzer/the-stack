# 压缩权衡

> 压缩减少网络传输和磁盘占用，但消耗 CPU。本文讲清压缩算法的选择、端到端压缩的工作方式、以及如何在 CPU 和带宽之间找到平衡。

## 1. 压缩在哪里发生

```txt
Producer 压缩 → Broker 存储压缩数据 → Consumer 解压
```

Broker 通常不解压数据，只存储和转发压缩后的字节。压缩和解压的 CPU 开销由生产者和消费者承担。

## 2. 算法对比

| 算法 | 压缩比 | 压缩速度 | 解压速度 | CPU 开销 | 适用场景 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| none | 1:1 | - | - | 无 | 低延迟场景 |
| gzip | 1:3~1:10 | 慢 | 慢 | 高 | 存储敏感，低吞吐 |
| snappy | 1:2~1:5 | 快 | 快 | 低 | 通用场景 |
| lz4 | 1:2~1:5 | 极快 | 极快 | 低 | 高吞吐场景 |
| zstd | 1:3~1:8 | 中 | 快 | 中 | Kafka 2.1+，平衡场景 |

## 3. 怎么选

| 场景 | 推荐 | 理由 |
| :-- | :-- | :-- |
| 高吞吐、CPU 充足 | lz4 | 压缩速度和解压速度都最快 |
| 带宽敏感、CPU 充足 | zstd | 压缩比最高，解压速度也不错 |
| CPU 敏感 | none 或 snappy | 最低 CPU 开销 |
| 存储敏感、低吞吐 | gzip | 压缩比高，但慢 |
| 不确定 | lz4 | 最安全的默认选择 |

## 4. 批量大小影响压缩比

压缩算法对更大的数据块效果更好。批次越大，压缩比越高：

```java
// 大批次 + 压缩 = 最佳效果
props.put("batch.size", 65536);    // 64KB
props.put("linger.ms", 50);        // 等更久攒更多消息
props.put("compression.type", "lz4");
```

| 批次大小 | lz4 压缩比 |
| :-- | :-- |
| 1KB | ~1.5:1 |
| 16KB | ~2.5:1 |
| 64KB | ~3:1 |

## 5. 端到端压缩配置

```java
// 生产者：压缩消息
props.put("compression.type", "zstd");
props.put("batch.size", 65536);
props.put("linger.ms", 20);

// Broker：不需要额外配置，默认不重新压缩

// 消费者：不需要额外配置，自动根据消息头解压
```

## 6. Broker 端压缩 vs 生产者端压缩

| 特性 | 生产者端压缩 | Broker 端压缩 |
| :-- | :-- | :-- |
| 谁承担 CPU | Producer | Broker |
| 网络传输 | 压缩后传输，带宽节省 | 原始数据传输，带宽浪费 |
| 推荐 | ✅ 生产环境推荐 | 仅用于特殊场景 |

> 始终在生产者端压缩。Broker 端压缩只在生产者无法压缩时（如旧版本客户端）才考虑。
