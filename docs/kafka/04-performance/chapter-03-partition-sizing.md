# 分区数选择

> 分区数是一个"选了就很难改"的决策。太少限制并行度，太多增加运维成本。本文给出选型依据和扩展风险。

## 1. 分区数决定了什么

| 维度 | 分区数的影响 |
| :-- | :-- |
| 消费并行度 | 分区数 = 消费并行度的天花板 |
| 生产并行度 | 多分区可以并行写入不同 Broker |
| Leader 选举速度 | 分区越多，故障恢复越慢 |
| Controller 压力 | 元数据管理开销随分区数增长 |
| 文件句柄 | 每个分区对应多个文件 |

## 2. 经验公式

```txt
分区数 = max(生产者并发数, 消费者并发数)
```

| 场景 | 建议分区数 |
| :-- | :-- |
| 低吞吐（<1万/s） | 3~6 |
| 中等吞吐（1~10万/s） | 10~30 |
| 高吞吐（>10万/s） | 50~100 |
| 极高吞吐（>100万/s） | 100~200 |

## 3. 分区过多的代价

| 代价 | 说明 |
| :-- | :-- |
| Leader 选举慢 | 每个分区都需要选举，分区越多越慢 |
| Controller 压力大 | 元数据管理开销增加 |
| 文件句柄多 | 每个分区对应多个文件（.log, .index, .timeindex） |
| 端到端延迟增加 | 元数据与副本同步的协调开销增大 |
| 内存占用增加 | 每个分区的索引和缓冲区消耗内存 |

> 分区数超过 1000 时，Controller 故障恢复时间会显著增加。如果需要更多并行度，建议先优化消费者处理速度。

## 4. 分区扩展

分区数只能增加、不能减少。

```bash
kafka-topics.sh --alter --topic my-topic --partitions 12 --bootstrap-server localhost:9092
```

### 扩展风险

| 风险 | 说明 |
| :-- | :-- |
| Key 路由变化 | 有 Key 的消息 rehash 后可能路由到新分区，破坏顺序 |
| 消费者 Rebalance | 分区数变化触发 Rebalance |
| 数据倾斜 | 新分区没有历史数据，短期内数据不均衡 |

### 扩展前的检查清单

1. 该 Topic 是否依赖 Key 的顺序性？如果是，扩展分区会破坏顺序
2. 消费者组中有多少个消费者？扩展后是否需要增加消费者
3. 是否在低峰期执行？扩展会触发 Rebalance，影响消费

## 5. 分区数 vs 消费者数

```txt
消费者数 ≤ 分区数：每个消费者至少分配一个分区
消费者数 > 分区数：多余的消费者空闲，浪费资源
```

最佳实践：消费者数 = 分区数，或略少于分区数（预留一个消费者做热备）。
