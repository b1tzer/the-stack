# 副本机制

## 1. 副本的作用

| 作用 | 说明 |
| :-- | :-- |
| **高可用** | 主分片故障时，副本提升为主分片 |
| **读扩展** | 搜索请求可以发送到副本分片 |
| **数据安全** | 数据在多个节点上存储多份 |

## 2. 副本同步机制

写入文档时，主分片负责写入，然后同步到所有副本分片：

```txt
Client → Coordinating Node → Primary Shard
                                  ↓
                            Replica Shard 1
                            Replica Shard 2
```

### 2.1 同步写入流程

1. 客户端发送写入请求到协调节点
2. 协调节点路由到主分片
3. 主分片执行写入操作
4. 主分片将请求转发到所有副本分片
5. 副本分片写入成功后返回确认
6. 主分片返回成功给协调节点
7. 协调节点返回客户端

> **注意**：副本同步是同步操作（默认），主分片会等待所有副本确认后才返回客户端。这保证了数据一致性，但增加了写入延迟。

## 3. 副本配置

```json
// 创建索引时设置副本数
PUT /my-index
{
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 2
  }
}

// 动态修改副本数
PUT /my-index/_settings
{
  "number_of_replicas": 1
}
```

## 4. 故障恢复

### 4.1 主分片故障

```txt
1. Master 检测到主分片所在节点故障
2. Master 从副本分片中选择一个提升为新的主分片
3. 更新集群路由表
4. 如果有其他副本需要同步，执行同步
5. 集群状态恢复 Green
```

### 4.2 副本分片故障

```txt
1. Master 检测到副本分片所在节点故障
2. 标记该副本为未分配
3. 如果有足够节点，重新分配副本
4. 从主分片同步数据到新副本
```

### 4.3 节点重启恢复

```json
// 查看恢复状态
GET /_cat/recovery?v

// 查看特定索引的恢复状态
GET /my-index/_recovery?pretty
```

## 5. 副本数量建议

| 场景 | 副本数 | 说明 |
| :-- | :-- | :-- |
| 开发/测试 | 0 | 单节点，不需要冗余 |
| 生产环境 | 1 | 标准配置，1 份副本 |
| 高可用要求 | 2 | 能容忍 2 个节点同时故障 |
| 读密集型 | 1~2 | 副本分担搜索压力 |

## 6. 副本与读扩展

搜索请求默认会被发送到所有分片（主分片 + 副本分片），实现读负载均衡：

```json
// 搜索时指定偏好
GET /my-index/_search?preference=_primary
{
  "query": { "match_all": {} }
}
```

| preference | 说明 |
| :-- | :-- |
| `_primary` | 只查询主分片 |
| `_replica` | 只查询副本分片 |
| `_local` | 优先查询本节点分片 |
| `_only_nodes:node-1` | 只查询指定节点 |

## 7. 最佳实践

- 生产环境至少 1 个副本
- 副本数不能超过数据节点数 - 1
- 批量写入时临时关闭副本，写完后恢复
- 监控未分配副本数量，及时排查原因
- 使用 `preference` 参数优化查询路由
- 单节点集群设置 `number_of_replicas: 0`
