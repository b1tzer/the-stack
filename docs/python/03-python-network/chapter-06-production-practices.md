# 网络 IO 的生产实践

本页面向已经能用 requests / httpx 发请求、想搞清楚"生产环境里大家到底怎么选、怎么配"的读者，回答一个问题：把 HTTP 客户端放进真实服务后，选库、连接池、超时重试和生命周期分别该按什么原则定。前置知识是 [HTTP 客户端基础](./chapter-01-http-client.md)和 [HTTP 客户端进阶](./chapter-04-http-advanced.md)。

示例基于 requests 2.x、httpx 0.28、aiohttp 3.14 和 Python 3.13+。

## 1. 怎么选库

选库先看代码运行在同步还是异步上下文，再看是否需要 HTTP/2：

- **同步代码**：`requests` 仍是事实标准，接口最简单、生态最全。它默认每个主机最多复用 10 条连接（`pool_maxsize=10`）。
- **异步代码**：`httpx` 提供和 requests 几乎一致的接口，同步异步一套 API，还支持 HTTP/2（`http2=True`）；`aiohttp` 是纯异步实现，性能更好、也是 FastAPI 底层的依赖，但 API 和同步库差异大、学起来更重。
- **需要 HTTP/2**：用 `httpx` 开启 `http2=True`；`requests` 不支持。

原则是**一个服务里尽量只用一种客户端**，避免同一套超时、重试、鉴权逻辑要在两套 API 里维护两遍。异步服务里混入 `requests` 会阻塞事件循环，这是[异步章节](../01-python-language/chapter-11-asyncio.md)反复强调的坑。

## 2. 连接池大小按并发量配

连接池决定了"同时能有多少条到下游的连接"。默认值只是起点：`requests` 是 10，`httpx` 是 100。

配置时看两个数：你的服务**同时会发多少个请求**，以及**下游能承受多少连接**。池子小于并发请求数，请求会排队等连接，等不到就超时；池子远大于实际并发，等于白占下游和你本机的连接、端口和内存。实践中先量出峰值并发，再让池子上限略高于它，并观察下游的连接数和本机端口占用做微调，而不是拍一个"大一点更好"的数。

## 3. 超时和重试要区分场景

超时里最关键的是把"连不上"和"响应慢"分开：连接超时设短（几秒），让网络不通快速失败；读取超时按接口真实耗时设，慢接口和下载要放宽。所有请求都要显式设超时——`requests` 默认超时是 `None`，也就是**无限等**，一个挂起的下游能拖垮整个调用链。

重试只对**幂等**操作（GET、以及明确幂等的接口）开启，并且要限制次数和退避。写操作重复执行可能产生副作用（重复下单、重复扣款），所以 POST/PUT 默认不重试。重试还要带指数退避，避免故障时所有调用方同时重试、把下游压成雪崩。

## 4. client 要复用，退出要优雅

连接池的价值来自复用，所以 client 应该作为长期对象存在：Web 服务在启动时创建一个全局 client，进程退出时关闭，而不是每请求新建。请求间共享的还有 TLS 会话和 DNS 缓存，新建即弃等于每次都重新握手、重新解析。

关闭也要优雅：`httpx` 用 `await client.aclose()` 或 `async with`，`requests` 用 `session.close()`。直接让进程退出或不管 client，连接池里已经建立的 TCP 连接可能来不及正常关闭，造成对端短暂的连接重置。

## 5. 常见坑

- **在异步代码里用同步客户端**：`requests` 的调用会阻塞事件循环，导致所有协程一起卡住。异步服务里 IO 必须用异步库。
- **连接泄漏**：每次请求新建 client 且不关闭，或 `stream` 响应没有读完就丢弃，连接不会被归还池子，慢慢把文件描述符和端口耗尽。
- **忘了设超时**：默认无超时（`requests`）或默认 5 秒（`httpx`）都不等于"适合你的下游"，一定要显式设。
- **重试非幂等请求**：把 POST 放进重试列表，等于默认允许重复执行写操作。
- **DNS 解析耗时**：同步 `requests` 在高频调用时，DNS 解析会成为固定开销，复用 `Session` 能缓解；异步栈里一般由事件循环和底层库处理，但自建服务时仍要留意。

## 6. 这一章要记住的结论

同步用 `requests`、异步用 `httpx` 或 `aiohttp`，一个服务尽量只用一种；连接池按实际并发量配，超时区分连接和读取，重试只对幂等操作且带退避；client 作为长期对象复用并在退出时优雅关闭，避免连接泄漏和阻塞事件循环。
