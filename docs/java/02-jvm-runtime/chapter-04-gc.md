# 垃圾回收

> "Java 有 GC，不会内存泄漏"——这句话骗了太多人。GC 回收的是根不可达的对象，不是你的代码不让它回收的对象。ThreadLocal 里存了个大对象、没调 `remove()`；静态 `List` 一直在 `add()`、从未 `clear()`；短命对象被长命池引用——GC Roots 可达，GC 就不回收，OOM 迟早来。Java 的内存泄漏不是 `malloc` 没配 `free`，是引用忘断了。

## 1. 为什么需要 GC

C/C++ 手动管理内存（`malloc` / `free`），开发者负责分配和释放。常见问题：

- **内存泄漏**：分配了忘记释放
- **野指针**：释放后继续使用
- **Double Free**：释放两次导致崩溃

Java 的垃圾回收器（GC）自动识别和回收不再使用的对象。代价是 GC 需要消耗 CPU 时间，偶尔产生 **Stop-The-World（STW）** 停顿——GC 执行时所有应用线程暂停。

对于绝大多数应用，GC 的收益远大于代价。但理解 GC 的工作原理，才能在出现性能问题时做出正确的调优决策。

## 2. 如何判定对象存活

### 2.1 引用计数法（Java 不采用）

每个对象维护一个引用计数器，被引用时 +1，引用断开时 -1，计数为 0 则回收。

问题：**无法解决循环引用**。

```java
a.ref = b;
b.ref = a;
// a 和 b 互相引用，引用计数永远不为 0
// 但实际上两者都可以被回收（没有外部引用指向它们）
```

### 2.2 可达性分析（Java 采用）

从一组 **GC Roots** 出发，沿着引用链遍历，能到达的对象是存活的，不能到达的是垃圾。

```text
GC Roots
  ├─→ Object A → Object B → Object C（存活）
  │                    └──→ Object D（存活）
  └─→ Object E（存活）

Object F → Object G（垃圾，没有 GC Root 能到达）
```

**GC Roots 包括：**

- 虚拟机栈中引用的对象（正在执行的方法中的局部变量）
- 静态字段引用的对象
- 常量引用的对象
- JNI 引用的对象
- 被 `synchronized` 持有的对象

## 3. 四种引用类型

| 引用类型 | 回收时机 | 典型用途 |
| :-- | :-- | :-- |
| **强引用** | 永不回收（除非不可达） | 普通 `new` |
| **软引用** | 内存不足时回收 | 缓存（如图片缓存） |
| **弱引用** | 下次 GC 必定回收 | `WeakHashMap`、`ThreadLocal` |
| **虚引用** | 无法通过它获取对象 | 对象回收跟踪、NIO Cleaner |

```java
// 软引用：内存不足时才回收
SoftReference<byte[]> soft = new SoftReference<>(new byte[1024 * 1024]);
byte[] data = soft.get();  // 内存充足时返回对象，不足时返回 null

// 弱引用：下次 GC 一定回收
WeakReference<User> weak = new WeakReference<>(new User("Tom"));
System.gc();
User user = weak.get();  // 很可能已经是 null
```

`WeakHashMap` 是弱引用的典型应用——当 key 不再被其他地方引用时，GC 会自动清除对应的 entry。常用于实现不影响 GC 的缓存。

`ThreadLocal` 内部也使用弱引用——ThreadLocal 变量被回收后，线程的 ThreadLocalMap 中对应的 entry 的 key 变为 null，下次 GC 时 value 被回收。如果线程长期存活（如线程池），value 可能不会被及时回收，导致内存泄漏——这是 `ThreadLocal` 使用后必须调用 `remove()` 的原因。

## 4. 垃圾回收算法

GC 算法主要面临的问题是：**回收时，到底优先保吞吐、保空间利用率，还是保内存连续性？**没有一种算法能同时做到“回收快、零碎片、零额外空间、零移动成本”。这就是为什么 HotSpot 不会只押注一种算法，而是根据对象的存活特征组合使用不同算法。

| 算法 | 核心动作 | 最大优势 | 主要代价 | 更适合 |
| :-- | :-- | :-- | :-- | :-- |
| 标记-清除 | 标记存活对象后清理垃圾 | 实现直接，空间利用率高 | 产生碎片 | 可容忍碎片的区域 |
| 标记-复制 | 将存活对象复制到新空间 | 无碎片，分配快 | 需要预留额外空间 | 新生代 |
| 标记-整理 | 标记后把存活对象压缩到一端 | 无碎片，空间利用率高 | 移动对象、更新引用 | 老年代 |

### 4.1 标记-清除（Mark-Sweep）

当存活对象比例较高时，把所有存活对象整体复制一遍并不划算；先找出垃圾，再把垃圾清掉，是成本最低的第一步。

```text
回收前： [存活][垃圾][存活][垃圾][存活]
清除后： [存活][空洞][存活][空洞][存活]
```

优点：不需要额外的大块备用空间，思路直接。

缺点：会留下碎片。碎片多了之后，即使“总空闲空间”足够，也可能因为拿不到连续内存而分配失败，最终触发一次带整理的 Full GC。

CMS 的核心回收阶段就是典型的标记-清除思路。

### 4.2 标记-复制（Copying）

如果一个区域里的对象大多“朝生夕灭”，那么与其清理一地碎片，不如只把少数还活着的对象搬走，剩下整块空间一次性清空。

```text
From: [存活][垃圾][垃圾][存活][垃圾]
To  : [存活][存活][空洞][空洞][空洞]
```

优点：回收后内存连续，分配只需“指针碰撞”，非常快。

代价：需要预留额外空间作为 To Space；如果存活对象很多，复制成本会迅速升高。

因此它特别适合新生代。注意，“浪费一半空间”是算法层面的直观理解；HotSpot 新生代通过 `Eden + Survivor + Survivor` 的布局降低了这个代价，并不是机械地空着一半堆不用。

### 4.3 标记-整理（Mark-Compact）

老年代里的对象存活率通常更高，既不能接受大量碎片，也不适合像复制算法那样长期预留一整块对等空间，于是需要“边清理、边压缩”。

```text
整理前： [存活][垃圾][存活][垃圾][存活]
整理后： [存活][存活][存活][连续空闲空间......]
```

优点：回收后没有碎片，空间利用率高。

代价：移动对象并修正引用需要额外开销，停顿通常比单纯的标记-清除更重。

很多 Full GC 或老年代压缩都带有明显的标记-整理特征。

新生代更偏爱标记-复制，因为“死得快”；老年代更常依赖标记-清除或标记-整理，因为“活得久”。下一节的分代收集，本质上就是把这三种算法的取舍放到不同区域里分别发挥。

## 5. 分代收集思想

**分代思想的核心，不是把堆机械地切成几块，而是承认不同对象的寿命完全不同。** 如果所有对象都用同一种算法、同一种频率回收，短命对象会拖累长寿对象，长寿对象也会放大回收成本。

HotSpot 的经验假设是：**绝大多数对象朝生夕灭，只有少数对象会长期存活。** 据统计，90% 以上的对象在创建后很快就会被回收。既然对象的存活特征不同，就应该把它们分开管理、分别回收——这就是分代收集思想。

### 5.1 什么是分代思想

分代收集的本质是：**按对象年龄和存活特征划分区域，再为不同区域选择不同算法。**

```text
对象不是“平均寿命”的：
  一大批对象   → 创建后很快死亡
  少数对象     → 多次 GC 后仍然存活

因此 JVM 的策略不是“一把尺子量到底”，而是：
  短命对象放在新生代   → 用标记-复制，回收快
  长寿对象放在老年代   → 用标记-清除 / 标记-整理，减少空间浪费
```

因此，JVM 通常将堆分为两代：

| 代 | 区域 | 特点 | 更常使用的算法 |
| :--- | :-- | :--- | :-- |
| 新生代 | Eden + S0 + S1 | 对象生命周期短，死亡率高 | 标记-复制 |
| 老年代 | Old | 对象生命周期长，存活率高 | 标记-清除 / 标记-整理 |

- **Young GC（Minor GC）**：回收新生代，频率高但速度快（通常 < 50ms）
- **Old GC / Full GC**：回收老年代（或整个堆），频率低但速度慢

### 5.2 对象如何进入老年代

对象并不是一创建就直接进入老年代。默认情况下，它会先在新生代里经历几轮回收，只有“活得够久”才会晋升。

```text
new → Eden
       ↓ Minor GC 存活
      Survivor（S0 或 S1）
       ↓ 每次 Minor GC 存活，年龄 +1
       ↓ 年龄达到阈值（默认 15）
      Old（老年代）
```

这套设计的意义很直接：**让大量短命对象在新生代快速回收，不要过早进入老年代制造更重的回收负担。**

### 5.3 跨代引用问题

分代思想解决了“不同对象该怎么分别回收”的问题，但也带来了新的工程问题：**如果老年代对象引用了新生代对象，Minor GC 时怎么知道这个新生代对象还活着？**

最笨的办法，是每次 Minor GC 都把整个老年代扫描一遍。但老年代通常很大，这会让本来应该很快的新生代回收变得越来越慢。

解决方案是：**记忆集（Remembered Set）+ 卡表（Card Table）**。

```text
卡表（Card Table）：
  堆被划分为 512 字节的“卡页”（Card Page）
  每个卡页对应卡表中的 1 字节（标记位）

  当老年代对象修改引用、指向新生代对象时：
  → 写屏障（Write Barrier）把对应卡页标记为 dirty
  → Minor GC 时只扫描 dirty 卡页，而不是扫描整个老年代
```

写屏障是 JVM 在引用赋值操作前后插入的代码，用来保证卡表信息始终准确。这不是程序员手动维护的，而是 JVM 自动完成的。

G1 收集器更进一步。每个 Region 都维护自己的 RSet（Remembered Set），记录“哪些外部 Region 有引用指向本 Region”。这比全堆共享一张卡表更精确，但代价是 RSet 本身会额外占用一部分内存（约 5%~10% 堆空间）。

## 6. HotSpot 垃圾收集器演进

前面已经讲了算法和分代，但读到这里，很多人还是会问：**为什么 HotSpot 里会有这么多 GC 名字？** 因为垃圾回收从来不是单目标优化：有的业务更怕停顿，有的业务更怕吞吐下降，有的业务堆很小，有的业务堆大到几十 GB 甚至 TB 级。

### 6.1 为什么会有这么多 GC（先理解分代与组合）

在经典 HotSpot 里，一套完整的 GC 方案，往往不是一个收集器独立完成，而是 **“新生代收集器 + 老年代收集器”** 的组合。

```text
新生代：对象多、死得快
  → 关注回收速度和分配速度
  → 更适合复制算法

老年代：对象少、活得久
  → 关注空间利用率和碎片控制
  → 更适合标记-清除 / 标记-整理

于是 HotSpot 的思路变成：
  为新生代选一个收集器
  + 为老年代选一个收集器
  = 拼成一套完整 GC 方案
```

这就是为什么你会同时看到 `Serial`、`ParNew`、`Parallel Scavenge`、`CMS`、`Parallel Old` 这些名字。它们很多不是彼此完全替代的关系，而是**分工不同、可以搭配使用**。

| 关注目标 | 新生代侧更看重 | 老年代侧更看重 | 典型组合 |
| :--- | :--- | :--- | :--- |
| 简单稳定 | 单线程、实现简单 | 单线程、实现简单 | `Serial + Serial Old` |
| 低延迟 | 年轻代尽快回收 | 老年代尽量并发 | `ParNew + CMS` |
| 高吞吐 | 多线程并行回收 | 多线程并行整理 | `Parallel Scavenge + Parallel Old` |

后来 G1、ZGC、Shenandoah 之所以显得更像“一整套 GC 产品”，是因为它们逐渐弱化了这种固定搭配关系：要么改成整堆分区回收，要么进一步把对象移动也做成并发。

### 6.2 GC 的历史演进（Serial/CMS/Parallel → G1 → ZGC/Shenandoah）

HotSpot 收集器的演进，不是按“新版本覆盖旧版本”的单线条路线走，而是沿着**简单、吞吐、低延迟、大堆**这几条压力线不断分叉，再逐步收束。

```text
早期分代组合时代
  简单路线：Serial + Serial Old
  吞吐路线：Parallel Scavenge + Parallel Old
  低延迟路线：ParNew + CMS
        ↓
整堆分区时代
  G1
  → 不再强依赖固定的新生代 / 老年代收集器搭配
        ↓
超低延迟时代
  ZGC / Shenandoah
  → 重点解决“大堆下停顿仍然要极短”
```

如果只看主流服务端应用的默认选择，大致可以记成三步：

- **第一阶段**：先解决“能不能把垃圾高效回收掉”
- **第二阶段**：再解决“回收时能不能别停太久”
- **第三阶段**：继续解决“堆很大时能不能仍然几乎不停”

### 6.3 新生代与老年代如何协作（Young GC、Old GC、Full GC）

分代之后，真正运行时发生的事情不是“某个 GC 名字在工作”，而是**新生代和老年代在不同压力下分工协作**。

```text
new object
   ↓
Eden
   ↓ Young GC 后仍存活
Survivor
   ↓ 多次存活、年龄增长
Old
```

可以把三种常见回收理解成三层压力响应：

- **Young GC**：只回收新生代。频率高、速度快，目标是尽快清掉大量短命对象。
- **Old GC**：主要处理老年代压力。它比 Young GC 更重，因为老年代对象存活率更高、回收成本更大。
- **Full GC**：对整个堆做一次更彻底的回收，通常停顿最长，也是最不希望频繁看到的情况。

这里要注意一个术语细节：**`Major GC` 在不同资料和日志里的用法并不总一致。** 有的文章把它等同于老年代回收，有的实现里又和 Full GC 混着说。为了避免歧义，这里直接用 **Young GC / Old GC / Full GC** 来描述。

它们的协作逻辑通常是这样的：

```text
1. 大量对象先在新生代分配
2. Young GC 回收新生代垃圾
3. 少数幸存对象晋升到老年代
4. 老年代占用持续升高后，触发 Old GC 或更重的回收
5. 如果空间仍不足、碎片过多，或者收集器无法完成预期回收，就可能进入 Full GC
```

这也解释了一个常见现象：**Young GC 本身不一定可怕，频繁 Full GC 才通常意味着系统已经进入危险区。**

### 6.4 经典组合（Serial+Serial Old、ParNew+CMS、Parallel Scavenge+Parallel Old）

在 G1 之前，HotSpot 的主流思路就是“给新生代选一个收集器，再给老年代选一个收集器”。下面这三组，是最有代表性的经典组合。

#### 6.4.1 Serial + Serial Old

- **发布时期**：属于 HotSpot 早期就存在的基础方案，典型可追溯到 `JDK 1.3.x` 时代
- **使用场景**：小堆、单核、客户端模式，或者对停顿不敏感但希望实现最简单的场景
- **新生代算法**：复制
- **老年代算法**：标记-整理
- **核心特点**：单线程、全程 STW，实现最直接，调优复杂度最低

这是最朴素的一套组合。它的优点不是“快”，而是**简单、稳定、额外开销低**。如果堆不大、CPU 也不多，多线程 GC 反而未必划算。

#### 6.4.2 ParNew + CMS

- **发布时期**：`CMS` 代表的是 `JDK 1.4.2` 开始进入主流视野的低停顿路线，`ParNew` 作为年轻代搭档长期与它配合使用
- **使用场景**：早期对响应时间敏感的 Web 服务、交互式系统
- **新生代算法**：复制（`ParNew` 是 `Serial` 的多线程年轻代版本）
- **老年代算法**：标记-清除（`CMS`）
- **核心特点**：尽量把老年代回收做成并发，以缩短长停顿

这套组合曾经非常经典，因为它第一次大规模把问题从“回收效率”转向“停顿体验”。`ParNew` 负责把年轻代快速收掉，`CMS` 负责在老年代尽量并发标记、并发清除。

它的代价也很明显：

- `CMS` 会产生碎片
- 并发阶段会吃 CPU
- 可能出现 **Concurrent Mode Failure**，退化成一次更重的 STW 回收

所以它解决了“停顿太长”的一部分问题，但没有彻底解决“大堆 + 碎片 + 低延迟”这组矛盾。`CMS` 已在 JDK 14 被移除。

#### 6.4.3 Parallel Scavenge + Parallel Old

- **发布时期**：`Parallel Scavenge` 在 `JDK 1.4.2` 一代进入主流，`Parallel Old` 到 `JDK 6` 才把这条吞吐路线补成完整组合
- **使用场景**：批处理、后台计算、数据分析这类吞吐优先的任务
- **新生代算法**：复制（`Parallel Scavenge`）
- **老年代算法**：标记-整理（`Parallel Old`）
- **核心特点**：多线程并行 GC，核心目标是让单位时间内完成更多工作

这套组合不追求“每次停顿都短”，而是追求**整体吞吐量高**。如果业务可以接受明显停顿，但更在意总处理能力，它通常比低延迟路线更合适。

### 6.5 整堆收集器（G1）

G1 出现的背景是：`CMS` 虽然降低了停顿，但碎片问题始终在；堆一大，回收和压缩的代价又会上来。HotSpot 需要一种更适合中大堆、停顿时间更可预测的方案。G1 收集器在 `JDK 7u4` 开始可用，`JDK 9` 成为 HotSpot 默认收集器

G1 的关键变化不是“取消分代”，而是**把整堆切成很多大小相等的 Region，再按 Region 组织年轻代、老年代和大对象区域**。

```text
┌───┬───┬───┬───┬───┬───┐
│ E │ E │ S │ O │ O │ H │  E=Eden, S=Survivor, O=Old
├───┼───┼───┼───┼───┼───┤  H=Humongous（大对象）
│ O │ E │   │ O │ S │   │
├───┼───┼───┼───┼───┼───┤
│   │ O │ E │   │ O │   │
└───┴───┴───┴───┴───┴───┘
```

- **使用场景**：中大堆、服务端在线系统，希望在吞吐和停顿之间取平衡，并要求停顿时间可预测
- **核心算法路线**：按 Region 回收，年轻代回收偏复制，老年代回收带整理特征
- **关键能力**：通过并发标记 + 按收益回收 Region，把“整堆一次性重扫”的压力拆小

G1 里最值得记住的是两类回收：

- **Young GC**：主要回收年轻代 Region
- **Mixed GC**：在回收年轻代的同时，顺带回收一部分垃圾收益最高的老年代 Region

也就是说，G1 不再像早期组合那样把“年轻代收集器”和“老年代收集器”死板地配成一对，而是用一套统一框架同时协调两边。

从 JDK 9 开始，G1 成为 HotSpot 默认收集器。

### 6.6 超低延迟收集器（ZGC、Shenandoah）

当堆继续变大，哪怕 G1 的停顿已经“可预测”，对某些业务来说仍然不够。比如大内存缓存、实时交易、搜索推荐这类系统，可能连几十毫秒的停顿都很敏感。

这时候问题已经变成：**能不能不仅并发标记，还把对象转移 / 整理也尽量并发化？**

#### 6.6.1 ZGC

- **发布时期**：`JDK 11` 引入（实验特性），`JDK 15` 起进入生产可用阶段
- **使用场景**：超大堆、极度关注延迟、能接受一定吞吐和实现复杂度代价的在线服务
- **核心算法路线**：并发整理；借助染色指针、读屏障、并发转移，把 STW 压到极短
- **核心特点**：停顿时间几乎不随堆大小线性放大，适合 TB 级堆

ZGC 的关键不是“完全没有 STW”，而是**把必须 STW 的阶段压缩到极短，把最重的对象移动放到并发阶段**。这也是它和传统分代组合、G1 的根本差异。

JDK 21 引入了分代 ZGC（`-XX:+UseZGC -XX:+ZGenerational`），进一步把“低延迟”与“分代回收效率”结合起来。JDK 23 起，分代 ZGC 成为默认行为。

#### 6.6.2 Shenandoah

- **发布时期**：`JDK 12` 进入 OpenJDK 视野（实验特性），随后在较新的 OpenJDK 发行版中逐步成熟
- **使用场景**：同样面向大堆和低延迟场景，尤其适合使用对应 OpenJDK / Red Hat 发行版的服务
- **核心算法路线**：并发整理；通过 Brooks Pointer 和读 / 写屏障完成并发转移
- **核心特点**：目标与 ZGC 相似，但工程实现路径不同

`Shenandoah` 和 `ZGC` 要解决的是同一类问题：**大堆下仍要把停顿压得很低**。差异主要不在目标，而在实现机制。

| 维度 | ZGC | Shenandoah |
| :-- | :-- | :-- |
| 目标 | 超低延迟 | 超低延迟 |
| 关键机制 | 染色指针 + 读屏障 | 转发指针 + 读/写屏障 |
| 整理方式 | 并发转移 | 并发转移 |
| 更适合记住的点 | 停顿极短，适合超大堆 | 目标相同，实现路径不同 |

如果只记一句判断：**G1 是主流服务端的平衡型选择，ZGC / Shenandoah 是更激进的低延迟选择。**

## 7. GC 日志分析

GC 日志是调优的第一手资料。

### 7.1 开启 GC 日志

```bash
# JDK 9+ 统一格式
-Xlog:gc*=info:file=gc.log:time,uptime,level,tags

# 更详细的 GC 日志
-Xlog:gc*=debug:file=gc.log:time,uptime,level,tags
```

### 7.2 解读 G1 GC 日志

```text
[2024-01-15T10:30:15.123+0800] GC(42) Pause Young (Normal) 
    [Eden: 1024M(1024M)->0B(1024M) 
     Survivors: 128M->128M 
     Old: 2048M->2100M]
    Metaspace: 45678K->45678K(1089536K)
   [123456K->98765K(4096M)]
    [Times: user=0.15 sys=0.02, real=0.08 secs]
```

| 字段 | 含义 |
| :-- | :-- |
| `Pause Young (Normal)` | Young GC，正常模式 |
| `Eden: 1024M(1024M)->0B(1024M)` | Eden 从 1024M 清空到 0 |
| `Old: 2048M->2100M` | 老年代从 2048M 增长到 2100M |
| `real=0.08 secs` | 实际停顿时间 80ms |
| `user=0.15` | GC 线程总 CPU 时间 150ms（多线程累加） |

### 7.3 从 GC 日志发现问题：实战案例

下面是一个实际的 GC 日志分析过程：

**现象：** 服务接口响应时间每隔几分钟飙升到 2 秒以上。

**第一步：看 GC 日志中的停顿时间**

```text
[10:30:15] Pause Young (Normal)  [Eden: 1024M->0B]  real=0.08 secs  ← 正常
[10:30:45] Pause Young (Normal)  [Eden: 1024M->0B]  real=0.07 secs  ← 正常
[10:31:15] Pause Mixed          [Eden: 1024M->0B  Old: 2048M->1800M]  real=0.15 secs
[10:31:30] Pause Full (Allocation Failure)  [Old: 3500M->3500M]  real=2.1 secs  ← 问题！
```

**第二步：分析 Full GC 原因**

`Allocation Failure` 意味着老年代空间不足，G1 无法在 Mixed GC 中回收足够空间，被迫 Full GC。老年代 3500M 几乎满。

**第三步：用 jmap 看哪些对象占用了老年代**

```bash
jmap -histo:live <pid> | head -20

# 输出:
#  num     #instances         #bytes  class name
#    1:       2500000      200000000  [B  (byte[])
#    2:       1800000      144000000  java.lang.String
#    3:         50000       40000000  com.example.CacheEntry
```

**第四步：定位代码**

`CacheEntry` 数量异常多 → 检查代码发现一个本地缓存没有设置过期策略，对象持续堆积在老年代。

**修复：** 为缓存添加 TTL 和最大条目数限制。修复后 Full GC 消失，接口响应时间稳定。

### 7.4 GC 选择决策树

```text
你的应用是什么类型？
├── 低延迟服务（Web、API、微服务）
│   ├── 堆 < 4GB → G1（默认，够用）
│   ├── 堆 4GB~16GB → G1 + 调优 MaxGCPauseMillis
│   └── 堆 > 16GB 或要求亚毫秒停顿 → ZGC（JDK 17+）
│
├── 高吞吐批处理（数据处理、ETL）
│   └── Parallel Scavenge（吞吐量优先，停顿可接受）
│
└── 小应用 / 客户端
    └── Serial（单线程，简单高效）
```

## 8. 核心 GC 参数

| 参数 | 说明 |
| :-- | :-- |
| `-Xms4g -Xmx4g` | 初始/最大堆大小（线上建议设为一致，避免动态扩缩） |
| `-Xmn2g` | 新生代大小 |
| `-XX:NewRatio=2` | 老年代:新生代 = 2:1 |
| `-XX:SurvivorRatio=8` | Eden:S0:S1 = 8:1:1 |
| `-XX:+UseG1GC` | 使用 G1 收集器 |
| `-XX:MaxGCPauseMillis=200` | G1 目标最大停顿时间 |
| `-XX:MaxTenuringThreshold=15` | 对象晋升老年代的年龄阈值 |
| `-XX:G1HeapRegionSize=8m` | G1 Region 大小 |
| `-XX:InitiatingHeapOccupancyPercent=45` | 触发并发标记的堆占用阈值 |
| `-XX:ConcGCThreads=4` | 并发 GC 线程数 |
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM 时自动 dump |
| `-Xlog:gc*:file=gc.log:time` | GC 日志（JDK 9+） |
