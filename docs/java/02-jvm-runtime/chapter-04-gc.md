# 垃圾回收

> “Java 有 GC，所以不会出现内存泄漏”并不准确。GC 只回收不再可达的对象。如果对象仍被 GC Roots 直接或间接引用，它就会继续存活；例如静态集合持续增长，或线程池中的 `ThreadLocal` 长期保留对象。Java 中的内存泄漏通常表现为可达但已无业务用途的对象持续累积。

## 1. 为什么需要 GC

C/C++ 手动管理内存（`malloc` / `free`），开发者负责分配和释放。常见问题：

- **内存泄漏**：分配了忘记释放
- **野指针**：释放后继续使用
- **Double Free**：释放两次导致崩溃

Java 的垃圾回收器（GC）自动识别和回收不再使用的对象。代价是 GC 需要消耗 CPU 时间，偶尔产生 **Stop-The-World（STW）** 停顿——GC 执行时所有应用线程暂停。

对于绝大多数应用，GC 的收益远大于代价。但理解 GC 的工作原理，才能在出现性能问题时做出正确的调优决策。

## 2. 如何判定对象存活

### 2.1 引用计数法（Java 不采用）

每个对象维护一个引用计数器，被引用时 +1，引用断开时 -1，计数为 0 则回收。

问题：**无法解决循环引用**。

```java
a.ref = b;
b.ref = a;
// a 和 b 互相引用，引用计数永远不为 0
// 但实际上两者都可以被回收（没有外部引用指向它们）
```

### 2.2 可达性分析（Java 采用）

从一组 **GC Roots** 出发，沿着引用链遍历，能到达的对象是存活的，不能到达的是垃圾。

```txt
GC Roots
  ├─→ Object A → Object B → Object C（存活）
  │                    └──→ Object D（存活）
  └─→ Object E（存活）

Object F → Object G（垃圾，没有 GC Root 能到达）
```

**GC Roots 包括：**

- 虚拟机栈中引用的对象（正在执行的方法中的局部变量）
- 静态字段引用的对象
- 常量引用的对象
- JNI 引用的对象
- 被 `synchronized` 持有的对象

## 3. 四种引用类型

| 引用类型 | 回收时机 | 典型用途 |
| :-- | :-- | :-- |
| **强引用** | 只要可达就保留 | 普通 `new` |
| **软引用** | 空间压力下可回收，具体时机取决于 GC 策略 | 可重建的缓存 |
| **弱引用** | GC 判定对象仅弱可达时可清除 | `WeakHashMap`、某些缓存 |
| **虚引用** | 无法通过它获取对象 | 对象回收跟踪、NIO Cleaner |

```java
// 软引用：内存不足时才回收
SoftReference<byte[]> soft = new SoftReference<>(new byte[1024 * 1024]);
byte[] data = soft.get();  // 内存充足时返回对象，不足时返回 null

// 弱引用：GC 判定对象仅弱可达时可清除
WeakReference<User> weak = new WeakReference<>(new User("Tom"));
System.gc();            // 仅是请求；JVM 可以忽略
User user = weak.get(); // 可能仍非 null，不能用单次调用测试回收时序
```

`WeakHashMap` 是弱引用的典型应用——当 key 不再被其他地方引用时，GC 会自动清除对应的 entry。常用于实现不影响 GC 的缓存。

`ThreadLocal` 的键使用弱引用，但这不会保证关联值随下一次 GC 一起回收。键失效后，value 可能通过 entry 间接保持可达，直到 `ThreadLocalMap` 在读取、写入或清理时移除陈旧条目。线程池中的线程长期存活，陈旧条目也可能长期存在，因此应按作用域调用 `remove()`，避免保留不再需要的对象。

## 4. 垃圾回收算法

GC 算法主要面临的问题是：**回收时，到底优先保吞吐、保空间利用率，还是保内存连续性？** 没有一种算法能同时做到“回收快、零碎片、零额外空间、零移动成本”。这就是为什么 HotSpot 不会只押注一种算法，而是根据对象的存活特征组合使用不同算法。

| 算法 | 核心动作 | 最大优势 | 主要代价 | 更适合 |
| :-- | :-- | :-- | :-- | :-- |
| 标记-清除 | 标记存活对象后清理垃圾 | 实现直接，空间利用率高 | 产生碎片 | 可容忍碎片的区域 |
| 标记-复制 | 将存活对象复制到新空间 | 无碎片，分配快 | 需要预留额外空间 | 新生代 |
| 标记-整理 | 标记后把存活对象压缩到一端 | 无碎片，空间利用率高 | 移动对象、更新引用 | 老年代 |

### 4.1 标记-清除（Mark-Sweep）

当存活对象比例较高时，把所有存活对象整体复制一遍并不划算；先找出垃圾，再把垃圾清掉，是成本最低的第一步。

![标记-清除：回收前后堆内存形态](/java/gc-mark-sweep.svg)

优点：不需要额外的大块备用空间，思路直接。

缺点：会留下碎片。碎片多了之后，即使“总空闲空间”足够，也可能因为拿不到连续内存而分配失败，最终触发一次带整理的 Full GC。

CMS 的核心回收阶段就是典型的标记-清除思路。

### 4.2 标记-复制（Copying）

如果一个区域里的对象大多“朝生夕灭”，那么与其清理一地碎片，不如只把少数还活着的对象搬走，剩下整块空间一次性清空。

![标记-复制：From 与 To 的内存形态](/java/gc-mark-copy.svg)

优点：回收后内存连续，分配只需“指针碰撞”，非常快。

代价：需要预留额外空间作为 To Space；如果存活对象很多，复制成本会迅速升高。

因此它特别适合新生代。注意，“浪费一半空间”是算法层面的直观理解；HotSpot 新生代通过 `Eden + Survivor + Survivor` 的布局降低了这个代价，并不是机械地空着一半堆不用。

### 4.3 标记-整理（Mark-Compact）

老年代里的对象存活率通常更高，既不能接受大量碎片，也不适合像复制算法那样长期预留一整块对等空间，于是需要“边清理、边压缩”。

![标记-整理：回收前后堆内存形态](/java/gc-mark-compact.svg)

优点：回收后没有碎片，空间利用率高。

代价：移动对象并修正引用需要额外开销，停顿通常比单纯的标记-清除更重。

很多 Full GC 或老年代压缩都带有明显的标记-整理特征。

新生代更偏爱标记-复制，因为“死得快”；老年代更常依赖标记-清除或标记-整理，因为“活得久”。下一节的分代收集，本质上就是把这三种算法的取舍放到不同区域里分别发挥。

## 5. 分代收集思想

**分代思想的核心，不是把堆机械地切成几块，而是承认不同对象的寿命完全不同。** 如果所有对象都用同一种算法、同一种频率回收，短命对象会拖累长寿对象，长寿对象也会放大回收成本。

HotSpot 的经验假设是：**绝大多数对象朝生夕灭，只有少数对象会长期存活。** 据统计，90% 以上的对象在创建后很快就会被回收。既然对象的存活特征不同，就应该把它们分开管理、分别回收——这就是分代收集思想。

### 5.1 什么是分代思想

分代收集的本质是：**按对象年龄和存活特征划分区域，再为不同区域选择不同算法。**

```txt
对象不是“平均寿命”的：
  一大批对象   → 创建后很快死亡
  少数对象     → 多次 GC 后仍然存活

因此 JVM 的策略不是“一把尺子量到底”，而是：
  短命对象放在新生代   → 用标记-复制，回收快
  长寿对象放在老年代   → 用标记-清除 / 标记-整理，减少空间浪费
```

因此，JVM 通常将堆分为两代：

| 代 | 区域 | 特点 | 更常使用的算法 |
| :--- | :-- | :--- | :-- |
| 新生代 | Eden + S0 + S1 | 对象生命周期短，死亡率高 | 标记-复制 |
| 老年代 | Old | 对象生命周期长，存活率高 | 标记-清除 / 标记-整理 |

- **Young GC（Minor GC）**：回收新生代，频率高但速度快（通常 < 50ms）
- **Old GC / Full GC**：回收老年代（或整个堆），频率低但速度慢

### 5.2 对象如何进入老年代

对象并不是一创建就直接进入老年代。默认情况下，它会先在新生代里经历几轮回收，只有“活得够久”才会晋升。

```txt
new → Eden
       ↓ Minor GC 存活
      Survivor（S0 或 S1）
       ↓ 每次 Minor GC 存活，年龄 +1
       ↓ 年龄达到阈值（默认 15）
      Old（老年代）
```

这套设计的意义很直接：**让大量短命对象在新生代快速回收，不要过早进入老年代制造更重的回收负担。**

### 5.3 跨代引用问题

分代思想解决了“不同对象该怎么分别回收”的问题，但也带来了新的工程问题：**如果老年代对象引用了新生代对象，Minor GC 时怎么知道这个新生代对象还活着？**

最笨的办法，是每次 Minor GC 都把整个老年代扫描一遍。但老年代通常很大，这会让本来应该很快的新生代回收变得越来越慢。

解决方案是：**记忆集（Remembered Set）+ 卡表（Card Table）**。

![卡表机制：堆内卡页与堆外卡表数组的对应关系](/java/card-table.svg)

写屏障是 JVM 在引用赋值操作前后插入的代码，用来保证卡表信息始终准确。这不是程序员手动维护的，而是 JVM 自动完成的。

G1 收集器更进一步。每个 Region 都维护自己的 RSet（Remembered Set），记录“哪些外部 Region 有引用指向本 Region”。这比全堆共享一张卡表更精确，但代价是 RSet 本身会额外占用一部分内存（约 5%~10% 堆空间）。

## 6. HotSpot 垃圾收集器演进

前面已经讲了算法和分代。读到这里，很多人还是会问，为什么 HotSpot 里会有这么多 GC 名字。因为垃圾回收从来不是单目标优化，有的业务更怕停顿，有的业务更怕吞吐下降，有的业务堆很小，有的业务堆大到几十 GB 甚至 TB 级。这一章沿着这条线索，把收集器的演进和选择讲清楚。

### 6.1 为什么会有这么多 GC

一次回收同时面对几个相互拉扯的目标，没有一种收集器能同时把每个目标都做到最好。

| 目标 | 含义 | 典型诉求 |
| :-- | :-- | :-- |
| 吞吐量 | 单位时间内应用真正干活的时间占比 | 批处理、后台计算，能接受停顿但求总量 |
| 延迟 | 单次停顿时间的长短 | Web 服务、实时交易，停顿越短越好 |
| 堆大小 | 需要管理的堆规模 | 小堆几十 MB，大堆几十 GB 甚至 TB 级 |

追求吞吐的收集器，停顿往往较长；追求低延迟的收集器，往往要牺牲一部分吞吐和额外开销；堆越大，回收越难做得既快又无感。

这三个目标也对应了收集器演进的主线，先解决能不能把垃圾高效回收掉，再解决回收时能不能别停太久，最后解决堆很大时能不能仍然几乎不停。后面几节按这条主线展开。

### 6.2 经典分代收集器时代

在 G1 之前，HotSpot 的主流思路不是用一个收集器管整堆，而是给新生代选一个收集器，再给老年代选一个收集器，拼成一套方案。

为什么需要这个组合，第 5 章已经讲了分代思想，新生代对象死得快，适合复制算法；老年代对象活得久，适合标记-清除或标记-整理。既然两代对象的特征和最优算法不同，收集器自然也要分开选。

```txt
新生代：对象多、死得快
  → 关注回收速度和分配速度
  → 更适合复制算法

老年代：对象少、活得久
  → 关注空间利用率和碎片控制
  → 更适合标记-清除 / 标记-整理

于是 HotSpot 的思路变成：
  为新生代选一个收集器
  + 为老年代选一个收集器
  = 拼成一套完整 GC 方案
```

这就是为什么你会同时看到 `Serial`、`ParNew`、`Parallel Scavenge`、`CMS`、`Parallel Old` 这些名字。它们很多不是彼此完全替代，而是分工不同、可以搭配。

分代之后，运行时发生的回收分了三层：

- **Young GC**：只回收新生代，频率高、速度快
- **Old GC**：主要处理老年代压力，比 Young GC 更重
- **Full GC**：对整个堆做一次更彻底的回收，停顿最长，最不希望频繁出现

三层里，频繁 Full GC 通常意味着系统已经进入危险区，Young GC 本身不可怕。

> `Major GC` 在不同资料和日志里的用法并不总一致，有的等同于老年代回收，有的又和 Full GC 混着说。为避免歧义，本文统一用 Young GC / Old GC / Full GC。

### 6.3 三条路线的演进

经典分代时代，沿着简单、吞吐、低延迟三条压力线，各自演化出一条路线。

| 路线 | 目标 | 新生代 | 老年代 | 核心特点 |
| :-- | :-- | :-- | :-- | :-- |
| Serial | 简单稳定 | Serial（单线程复制） | Serial Old（单线程标记-整理） | 全程 STW，实现最直接 |
| Parallel | 高吞吐 | Parallel Scavenge（多线程复制） | Parallel Old（多线程标记-整理） | 并行回收，总吞吐最高 |
| CMS | 低延迟 | ParNew（多线程复制） | CMS（并发标记-清除） | 老年代尽量并发，缩短长停顿 |

#### 6.3.1 Serial，简单

`Serial + Serial Old` 是最朴素的一套，单线程、全程 STW，实现最直接，调优复杂度最低，典型可追溯到 JDK 1.3.x 时代。

它的优点不是快，而是简单、稳定、额外开销低。如果堆不大、CPU 也不多，多线程 GC 未必划算。适合小堆、单核、客户端模式。

#### 6.3.2 Parallel，吞吐量

`Parallel Scavenge + Parallel Old` 不追求每次停顿都短，而是追求整体吞吐量高。多线程并行 GC，核心目标是让单位时间内完成更多工作。`Parallel Scavenge` 在 JDK 1.4.2 一代进入主流，`Parallel Old` 到 JDK 6 才补全这条路线。

适合批处理、后台计算、数据分析这类吞吐优先的任务。如果业务可以接受明显停顿，但更在意总处理能力，这条路线比低延迟路线更合适。

#### 6.3.3 CMS，低延迟

`ParNew + CMS` 第一次大规模把问题从回收效率转向停顿体验。`ParNew` 负责把年轻代快速收掉，`CMS` 负责在老年代尽量并发标记、并发清除。这条路线代表 JDK 1.4.2 开始进入主流视野的低停顿方向。

代价也很明显：

- `CMS` 会产生碎片
- 并发阶段会吃 CPU
- 可能出现 Concurrent Mode Failure，退化成一次更重的 STW 回收

所以 CMS 解决了停顿太长的一部分问题，但没有彻底解决大堆、碎片、低延迟这组矛盾。CMS 已在 JDK 14 被移除。

### 6.4 G1，从收集器组合到统一管理整堆

G1 出现的背景是，`CMS` 虽然降低了停顿，但碎片问题始终在；堆一大，回收和压缩的代价又会上来。HotSpot 需要一种更适合中大堆、停顿时间更可预测的方案。G1 收集器在 `JDK 7u4` 开始可用，`JDK 9` 成为 HotSpot 默认收集器。

G1 的关键变化不是取消分代，而是**把整堆切成很多大小相等的 Region，再按 Region 组织年轻代、老年代和大对象区域**。

```txt
┌───┬───┬───┬───┬───┬───┐
│ E │ E │ S │ O │ O │ H │  E=Eden, S=Survivor, O=Old
├───┼───┼───┼───┼───┼───┤  H=Humongous（大对象）
│ O │ E │   │ O │ S │   │
├───┼───┼───┼───┼───┼───┤
│   │ O │ E │   │ O │   │
└───┴───┴───┴───┴───┴───┘
```

- **使用场景**：中大堆、服务端在线系统，希望在吞吐和停顿之间取平衡，并要求停顿时间可预测
- **核心算法路线**：按 Region 回收，年轻代回收偏复制，老年代回收带整理特征
- **关键能力**：通过并发标记 + 按收益回收 Region，把整堆一次性重扫的压力拆小

G1 里最值得记住的是两类回收：

- **Young GC**：主要回收年轻代 Region
- **Mixed GC**：在回收年轻代的同时，顺带回收一部分垃圾收益最高的老年代 Region

也就是说，G1 不再像早期组合那样把年轻代收集器和老年代收集器死板地配成一对，而是用一套统一框架同时协调两边。

### 6.5 ZGC / Shenandoah，进一步追求超低延迟

当堆继续变大，哪怕 G1 的停顿已经可预测，对某些业务来说仍然不够。大内存缓存、实时交易、搜索推荐这类系统，可能连几十毫秒的停顿都很敏感。

这时候问题已经变成，能不能不仅并发标记，还把对象转移、整理也尽量并发化。

#### 6.5.1 ZGC

- **发布时期**：`JDK 11` 引入（实验特性），`JDK 15` 起进入生产可用阶段
- **使用场景**：超大堆、极度关注延迟、能接受一定吞吐和实现复杂度代价的在线服务
- **核心算法路线**：并发整理；借助染色指针、读屏障、并发转移，把 STW 压到极短
- **核心特点**：停顿时间几乎不随堆大小线性放大，适合 TB 级堆

ZGC 的关键不是完全没有 STW，而是**把必须 STW 的阶段压缩到极短，把最重的对象移动放到并发阶段**。这也是它和传统分代组合、G1 的根本差异。

JDK 21 引入了分代 ZGC（`-XX:+UseZGC -XX:+ZGenerational`），进一步把低延迟与分代回收效率结合起来。JDK 23 起，分代 ZGC 成为默认行为。

#### 6.5.2 Shenandoah

- **发布时期**：`JDK 12` 进入 OpenJDK 视野（实验特性），随后在较新的 OpenJDK 发行版中逐步成熟
- **使用场景**：同样面向大堆和低延迟场景，尤其适合使用对应 OpenJDK / Red Hat 发行版的服务
- **核心算法路线**：并发整理；通过 Brooks Pointer 和读 / 写屏障完成并发转移
- **核心特点**：目标与 ZGC 相似，但工程实现路径不同

Shenandoah 和 ZGC 要解决的是同一类问题，大堆下仍要把停顿压得很低。差异主要不在目标，而在实现机制。

| 维度 | ZGC | Shenandoah |
| :-- | :-- | :-- |
| 目标 | 超低延迟 | 超低延迟 |
| 关键机制 | 染色指针 + 读屏障 | 转发指针 + 读/写屏障 |
| 整理方式 | 并发转移 | 并发转移 |

### 6.6 现在到底怎么理解和选择 GC

回到最初的三个目标，可以得出一张选择图：

```txt
堆很小、单核、客户端           → Serial
吞吐优先、能接受停顿           → Parallel Scavenge + Parallel Old
低延迟、中小堆                 → G1（JDK 9+ 默认，多数场景够用）
超低延迟、超大堆               → ZGC / Shenandoah
```

如果只记一句，主流服务端默认用 G1；对停顿极度敏感或堆特别大时换 ZGC；吞吐优先的离线任务用 Parallel。

更细的决策树见本页 §7.4，核心参数汇总见 §8。

## 7. GC 日志分析

GC 日志是调优的第一手资料。

### 7.1 开启 GC 日志

```bash
# JDK 9+ 统一格式
-Xlog:gc*=info:file=gc.log:time,uptime,level,tags

# 更详细的 GC 日志
-Xlog:gc*=debug:file=gc.log:time,uptime,level,tags
```

### 7.2 解读 G1 GC 日志

```txt
[2024-01-15T10:30:15.123+0800] GC(42) Pause Young (Normal) 
    [Eden: 1024M(1024M)->0B(1024M) 
     Survivors: 128M->128M 
     Old: 2048M->2100M]
    Metaspace: 45678K->45678K(1089536K)
   [123456K->98765K(4096M)]
    [Times: user=0.15 sys=0.02, real=0.08 secs]
```

| 字段 | 含义 |
| :-- | :-- |
| `Pause Young (Normal)` | Young GC，正常模式 |
| `Eden: 1024M(1024M)->0B(1024M)` | Eden 从 1024M 清空到 0 |
| `Old: 2048M->2100M` | 老年代从 2048M 增长到 2100M |
| `real=0.08 secs` | 该日志记录的墙上时间；是否直接等于应用停顿时间取决于收集器和日志字段定义 |
| `user=0.15` | GC 线程总 CPU 时间 150ms（多线程累加） |

### 7.3 从 GC 日志发现问题：实战案例

下面以一段构造的 GC 日志演示分析步骤，字段含义和格式会随 JDK 与收集器版本变化。

**现象：** 服务接口响应时间每隔几分钟飙升到 2 秒以上。

**第一步：看 GC 日志中的停顿时间**

```txt
[10:30:15] Pause Young (Normal)  [Eden: 1024M->0B]  real=0.08 secs  ← 正常
[10:30:45] Pause Young (Normal)  [Eden: 1024M->0B]  real=0.07 secs  ← 正常
[10:31:15] Pause Mixed          [Eden: 1024M->0B  Old: 2048M->1800M]  real=0.15 secs
[10:31:30] Pause Full (Allocation Failure)  [Old: 3500M->3500M]  real=2.1 secs  ← 问题！
```

**第二步：分析 Full GC 原因**

`Allocation Failure` 意味着老年代空间不足，G1 无法在 Mixed GC 中回收足够空间，被迫 Full GC。老年代 3500M 几乎满。

**第三步：用 jmap 看哪些对象占用了老年代**

```bash
# 可能触发 Full GC，生产环境仅在可接受额外停顿时使用
jmap -histo:live <pid> | head -20

# 输出:
#  num     #instances         #bytes  class name
#    1:       2500000      200000000  [B  (byte[])
#    2:       1800000      144000000  java.lang.String
#    3:         50000       40000000  com.example.CacheEntry
```

**第四步：定位代码**

`CacheEntry` 数量异常多 → 检查代码发现一个本地缓存没有设置过期策略，对象持续堆积在老年代。

**修复：** 为缓存添加 TTL 和最大条目数限制。修复后 Full GC 消失，接口响应时间稳定。

### 7.4 GC 选择决策树

```txt
你的应用是什么类型？
├── 低延迟服务（Web、API、微服务）
│   ├── 堆 < 4GB → G1（默认，够用）
│   ├── 堆 4GB~16GB → G1 + 调优 MaxGCPauseMillis
│   └── 堆 > 16GB 或要求亚毫秒停顿 → ZGC（JDK 17+）
│
├── 高吞吐批处理（数据处理、ETL）
│   └── Parallel Scavenge（吞吐量优先，停顿可接受）
│
└── 小应用 / 客户端
    └── Serial（单线程，简单高效）
```

## 8. 常用 GC 参数示例

| 参数 | 说明 |
| :-- | :-- |
| `-Xms4g -Xmx4g` | 初始/最大堆大小（线上建议设为一致，避免动态扩缩） |
| `-Xmn2g` | 新生代大小 |
| `-XX:NewRatio=2` | 老年代:新生代 = 2:1 |
| `-XX:SurvivorRatio=8` | Eden:S0:S1 = 8:1:1 |
| `-XX:+UseG1GC` | 使用 G1 收集器 |
| `-XX:MaxGCPauseMillis=200` | G1 目标最大停顿时间 |
| `-XX:MaxTenuringThreshold=15` | 对象晋升老年代的年龄阈值 |
| `-XX:G1HeapRegionSize=8m` | G1 Region 大小 |
| `-XX:InitiatingHeapOccupancyPercent=45` | 触发并发标记的堆占用阈值 |
| `-XX:ConcGCThreads=4` | 并发 GC 线程数 |
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM 时自动 dump |
| `-Xlog:gc*:file=gc.log:time` | GC 日志（JDK 9+） |

上表仅用于说明 G1 的部分常用参数。新生代比例、暂停目标及默认值会因收集器和 JDK 版本而异，应结合所用版本的官方参数文档与压测结果调整。
