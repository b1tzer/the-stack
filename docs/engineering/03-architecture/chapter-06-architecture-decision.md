# 架构决策记录（ADR）

> **核心问题**：如何记录和管理架构决策？ADR 的格式是什么？如何用 ADR 避免"决策失忆"？

## 1. 什么是 ADR

架构决策记录（Architecture Decision Record）是一种轻量级文档，记录项目中的重要技术决策及其上下文和理由。

## 2. ADR 模板

```markdown
# ADR-{编号}: {标题}

## 状态
提议 | 已接受 | 已废弃 | 已替代（被 ADR-XXX 替代）

## 上下文
描述决策的背景：面临的问题、约束条件、相关因素。

## 决策
明确陈述做出的决策。

## 后果
分析决策带来的正面和负面影响。
```

## 3. ADR 实战示例

```markdown
# ADR-001: 选择 PostgreSQL 作为主数据库

## 状态
已接受

## 上下文
项目需要一个关系型数据库来存储核心业务数据。
团队对 MySQL 和 PostgreSQL 都有经验。
数据模型包含 JSON 字段和地理空间数据。
预计数据量在 3 年内增长到 1 亿条记录。

## 决策
选择 PostgreSQL 作为主数据库。

理由：
1. 原生支持 JSONB 类型，适合半结构化数据
2. PostGIS 扩展支持地理空间查询
3. 更好的并发控制（MVCC 实现更成熟）
4. 窗口函数、CTE 等高级 SQL 特性支持更好
5. 许可证更自由（MIT-like License）

## 后果
正面：
- 可以直接存储 JSON 数据，无需额外的文档数据库
- 地理空间查询性能优秀
- 高级 SQL 特性减少应用层复杂度

负面：
- 团队部分成员需要学习 PostgreSQL 特性
- 运维工具链需要从 MySQL 生态切换
- 某些 ORM 的 PostgreSQL 方言可能有兼容性问题
```

## 4. 常见 ADR 分类

| 类别 | 示例决策 |
|------|---------|
| 技术选型 | 数据库、消息队列、缓存方案 |
| 架构风格 | 单体 vs 微服务、同步 vs 异步 |
| 设计模式 | 认证方案、支付集成方式 |
| 编码规范 | 错误处理策略、日志规范 |
| 基础设施 | 部署方案、监控告警 |

## 5. 管理 ADR 的最佳实践

```java
/**
 * ADR 管理最佳实践：
 * 
 * 1. 存储位置：docs/adr/ 目录，与代码一起版本管理
 * 2. 命名规则：ADR-{序号}-{简短标题}.md
 * 3. 编号规则：递增编号，不重用已废弃的编号
 * 4. 状态管理：及时更新状态（提议→已接受→已废弃）
 * 5. 团队评审：重大决策需要团队讨论后记录
 * 6. 定期回顾：每季度回顾 ADR，清理过时决策
 * 
 * 工具推荐：
 * - adr-tools：命令行工具（npm install -g adr-tools）
 * - adr-manager：VS Code 插件
 * - 简单方案：Markdown 文件 + Git 管理
 */
public class AdrBestPractices {
    // ADR 不是写给别人看的文档，而是写给未来的自己。
    // 6 个月后你不会记得"为什么选了 Redis 而不是 Memcached"。
    // ADR 帮你回答这个问题。
}
```

## 6. ADR 与 RFC 的区别

| 维度 | ADR | RFC |
|------|-----|-----|
| 目的 | 记录已做出的决策 | 征求意见，寻求共识 |
| 时机 | 决策做出后记录 | 决策做出前征求意见 |
| 范围 | 架构和技术决策 | 任何重要变更 |
| 形式 | 轻量级，1-2 页 | 通常更详细 |

> **核心原则**：最好的架构决策是那些你能在 6 个月后仍然理解其理由的决策。ADR 就是帮你做到这一点的工具。不需要长篇大论，关键是记录"为什么"。
