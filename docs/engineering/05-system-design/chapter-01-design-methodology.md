# 设计方法论

> 系统设计不是灵感创作，是有章可循的工程过程。

## 1. 系统设计四步法

```txt
1. 需求澄清 → 明确功能和非功能需求
2. 高层设计 → 画架构图，确定核心组件
3. 详细设计 → 深入关键组件的技术方案
4. 权衡讨论 → 讨论设计决策的 trade-off
```

## 2. 需求澄清

### 功能需求

- 核心功能是什么？
- 用户场景有哪些？
- API 接口怎么设计？

### 非功能需求

| 维度 | 需要问的问题 |
| :-- | :-- |
| 并发量 | QPS 是多少？峰值是多少？ |
| 数据量 | 存储多少数据？增长速度？ |
| 延迟 | P99 延迟要求？ |
| 可用性 | 几个 9？能容忍多长停机？ |
| 一致性 | 强一致还是最终一致？ |

## 3. 高层设计

```txt
Client → LB → App Server → Cache → DB
                      ↓
                  Message Queue → Worker
```

核心步骤：

1. 画数据流图
2. 确定核心组件
3. 定义组件间接口
4. 估算容量

## 4. 容量估算

```txt
假设：DAU = 1000万，每人每天 10 次操作
  QPS = 1000万 × 10 / 86400 ≈ 1200 QPS
  峰值 QPS ≈ 3 × 1200 = 3600 QPS

存储：每条记录 1KB，每天 1亿条
  日增量 = 1亿 × 1KB = 100GB/天
  年增量 = 100GB × 365 = 36TB/年
```

## 5. 常见设计模式

| 问题 | 方案 |
| :-- | :-- |
| 高并发读 | 缓存 + CDN + 读写分离 |
| 高并发写 | 消息队列 + 异步处理 |
| 大数据量 | 分库分表 + 冷热分离 |
| 高可用 | 主从 + 自动故障转移 |
| 低延迟 | 缓存 + 本地计算 |

## 6. 权衡讨论

每个设计决策都有 trade-off：

| 决策 | 选择 A | 选择 B |
| :-- | :-- | :-- |
| 数据库 | MySQL（成熟） | TiDB（分布式） |
| 缓存 | Redis（快） | Memcached（简单） |
| 消息队列 | RabbitMQ（低延迟） | Kafka（高吞吐） |
| 一致性 | 强一致（安全） | 最终一致（性能） |
