# Code Review

> **核心问题**：如何做好 Code Review？Review 的标准是什么？如何让 Code Review 成为团队文化？

## 1. Code Review 的价值

| 价值 | 说明 |
| :-- | :-- |
| 代码质量 | 发现 Bug、设计缺陷、代码坏味道 |
| 知识共享 | 团队成员了解彼此的代码 |
| 一致性 | 统一代码风格和设计模式 |
| 成长 | 新人从 Review 中学习，资深工程师通过 Review 教学 |

## 2. Code Review Checklist

```markdown
## Code Review 检查清单

### 正确性
□ 代码逻辑是否正确？
□ 边界条件是否处理？
□ 异常处理是否完善？
□ 并发安全是否考虑？

### 设计
□ 是否遵循 SOLID 原则？
□ 是否有代码坏味道？
□ 抽象层次是否合理？
□ 命名是否清晰？

### 可维护性
□ 代码是否易于理解？
□ 是否有适当的注释？
□ 是否有单元测试？
□ 测试覆盖率是否足够？

### 性能
□ 是否有 N+1 查询？
□ 是否有内存泄漏风险？
□ 是否有不必要的循环？

### 安全
□ 是否有 SQL 注入风险？
□ 是否有 XSS 风险？
□ 敏感数据是否加密？
```

## 3. Review 评论规范

```java
// 好的 Review 评论：具体、可操作、解释原因

// 差：模糊的评论
// "这段代码不好"

// 好：具体的评论
// "建议使用 StringBuilder 替代字符串拼接。在循环中使用 + 拼接字符串，
//  每次都会创建新的 String 对象，时间复杂度为 O(n²)。
//  StringBuilder 的时间复杂度为 O(n)。"

// 好：指出问题并给出解决方案
// "这里可能存在 N+1 查询问题。建议使用 @EntityGraph 或 JOIN FETCH：
//  @Query(\"SELECT o FROM Order o JOIN FETCH o.items WHERE o.userId = :userId\")"

// 好：认可好的代码
// "这个策略模式的使用很优雅，后续新增支付方式只需要添加新的实现类 👍"
```

## 4. Review 工具与流程

```java
// GitHub Pull Request 流程
// 1. 创建分支，开发功能
// 2. 提交 PR，填写描述
// 3. 自动触发 CI（构建 + 测试 + 代码扫描）
// 4. 指定 Reviewer 进行 Review
// 5. 根据反馈修改代码
// 6. 至少 1 人 Approve 后合并

// PR 描述模板
/**
 * ## 变更说明
 * 简述本次变更的内容和目的
 * 
 * ## 变更类型
 * - [ ] 新功能
 * - [ ] Bug 修复
 * - [ ] 重构
 * - [ ] 文档更新
 * 
 * ## 测试
 * - [ ] 单元测试已添加/更新
 * - [ ] 本地测试通过
 * 
 * ## 影响范围
 * 描述本次变更影响的功能模块
 * 
 * ## 截图（UI 变更时）
 */
```

## 5. Review 文化建设

| 实践 | 说明 |
| :-- | :-- |
| 小 PR | 每次 PR 控制在 200-400 行，便于 Review |
| 及时 Review | 收到 PR 后 24 小时内完成 Review |
| 正面反馈 | 认可好的代码，不只是挑问题 |
| 对事不对人 | 评论针对代码，不针对人 |
| 自我 Review | 提交 PR 前先自己 Review 一遍 |

> **核心原则**：Code Review 不是找茬，而是团队共同提升代码质量的过程。好的 Review 文化应该是"我们一起让代码更好"，而不是"我来挑你的毛病"。
