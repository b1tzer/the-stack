# 敏捷开发

## 1. Scrum

| 角色 | 职责 |
| :-- | :-- |
| Product Owner | 需求管理、优先级排序 |
| Scrum Master | 流程守护、障碍移除 |
| Development Team | 跨职能团队 |

| 仪式 | 频率 | 时长 |
| :-- | :-- | :-- |
| Sprint Planning | 每 Sprint 开始 | 2-4h |
| Daily Standup | 每天 | 15min |
| Sprint Review | 每 Sprint 结束 | 1-2h |
| Retrospective | 每 Sprint 结束 | 1h |

## 2. Kanban

- 可视化工作流
- 限制在制品（WIP）
- 管理流动
- 持续改进

## 3. 敏捷 vs 瀑布

| 特性 | 敏捷 | 瀑布 |
| :-- | :-- | :-- |
| 需求 | 可变 | 固定 |
| 交付 | 持续 | 一次性 |
| 反馈 | 快速 | 延迟 |
| 风险 | 早期发现 | 后期发现 |

## 4. Scrum 实战详解

### 4.1 用户故事模板

```markdown
# 用户故事

**作为** [角色]
**我想要** [功能]
**以便** [价值]

## 验收标准
- [ ] 条件 1
- [ ] 条件 2
- [ ] 条件 3

## 示例
作为 一个注册用户
我想要 修改我的收货地址
以便 在下单时选择正确的配送地址

验收标准：
- [ ] 用户可以添加最多 10 个收货地址
- [ ] 用户可以设置一个默认地址
- [ ] 地址信息包含：省、市、区、详细地址、收货人、手机号
- [ ] 手机号格式校验
```

### 4.2 Sprint Planning 实践

```markdown
# Sprint Planning 输出

## Sprint 目标
本 Sprint 完成订单取消功能的开发和测试。

## Sprint Backlog
| 任务 | 负责人 | 故事点 | 状态 |
| :-- | :-- | :-- | :-- |
| 订单取消 API | 张三 | 3 | TODO |
| 库存恢复逻辑 | 李四 | 2 | TODO |
| 退款对接 | 王五 | 5 | TODO |
| 前端取消页面 | 赵六 | 3 | TODO |
| 集成测试 | 张三 | 2 | TODO |

## 容量评估
团队速率：20 点/Sprint
本 Sprint 承诺：15 点（预留 buffer）
```

### 4.3 Daily Standup 实践

```markdown
# 每日站会（15 分钟）

每人回答三个问题：
1. 昨天完成了什么？
2. 今天计划做什么？
3. 有什么阻碍？

避免：
- 详细的技术讨论（会后单独讨论）
- 变成汇报会（是同步信息，不是汇报工作）
- 超过 15 分钟（设置计时器）
```

### 4.4 Sprint Retrospective 实践

```markdown
# 回顾会议模板

## 做得好的（继续保持）
- 代码评审质量提升
- 测试覆盖率从 60% 提升到 75%

## 需要改进的
- 需求变更太频繁，影响开发节奏
- 跨团队沟通效率低

## 行动项
| 行动 | 负责人 | 截止日期 |
| :-- | :-- | :-- |
| 建立需求变更审批流程 | PO | 下周五 |
| 每周与支付团队同步一次 | TL | 立即执行 |
```

## 5. Scrum vs Kanban 选型

| 维度 | Scrum | Kanban |
| :-- | :-- | :-- |
| 节奏 | 固定 Sprint（1-4 周） | 持续流动 |
| 角色 | PO、SM、Dev Team | 无固定角色 |
| 变更 | Sprint 内不接受变更 | 随时可加入新任务 |
| 适用场景 | 需求相对稳定 | 需求频繁变化、运维团队 |

> **敏捷的本质**：不是遵循某个框架的仪式，而是快速反馈、持续改进。如果站会变成了形式主义，那就改掉它。敏捷是手段，不是目的。
