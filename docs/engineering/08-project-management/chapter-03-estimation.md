# 估算

> **核心问题**：如何准确估算开发工期？故事点和理想人天有什么区别？

## 1. 估算方法

| 方法 | 说明 | 适用场景 |
| :-- | :-- | :-- |
| 故事点 | 相对估算，不直接对应时间 | Sprint 规划 |
| 理想人天 | 假设没有打扰的工作天数 | 项目规划 |
| Planning Poker | 团队投票达成共识 | 需求评审 |
| T-Shirt Size | S/M/L/XL 粗略估算 | 早期评估 |

## 2. Planning Poker 实践

```java
// Planning Poker 流程
// 1. PO 讲解用户故事
// 2. 团队成员提问澄清
// 3. 每人选择一张牌（故事点）
// 4. 同时亮牌
// 5. 估算差异大时讨论，重新投票
// 6. 达成共识

// 故事点斐波那契数列：1, 2, 3, 5, 8, 13, 21
// 1 = 极简单（几行代码）
// 3 = 中等（一个完整功能）
// 5 = 复杂（需要设计和多处修改）
// 8 = 非常复杂（需要调研和多模块改动）
// 13 = 极复杂（需要拆分为多个故事）
```

## 3. 速率（Velocity）计算

```java
// 速率 = 团队每个 Sprint 完成的故事点数
// 用途：预测未来 Sprint 能完成多少工作

// 示例：
// Sprint 1: 完成 18 点
// Sprint 2: 完成 22 点
// Sprint 3: 完成 20 点
// 平均速率: 20 点/Sprint

// 假设总需求 100 点
// 预计需要: 100 / 20 = 5 个 Sprint
```

## 4. 估算偏差分析

| 偏差原因 | 解决方案 |
| :-- | :-- |
| 需求理解不充分 | 评审时多提问，明确验收标准 |
| 技术方案不确定 | 预研/Spike，先验证再估算 |
| 遗漏边界条件 | 使用 Checklist 检查 |
| 依赖外部团队 | 将依赖风险纳入估算 |
| 过于乐观 | 参考历史数据，使用三点估算法 |

```java
// 三点估算法
// 期望值 = (乐观 + 4 × 最可能 + 悲观) / 6
// 示例：
// 乐观: 2 天
// 最可能: 3 天
// 悲观: 8 天
// 期望值 = (2 + 4×3 + 8) / 6 = 3.33 天
```

> **估算的核心**：估算不是承诺，而是预测。估算的目的是帮助团队做计划，而不是考核个人。允许偏差存在，重要的是持续改进估算的准确性。
