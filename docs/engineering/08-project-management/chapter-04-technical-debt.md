# 技术债务

> **核心问题**：什么是技术债务？如何识别、管理和偿还技术债务？

## 1. 技术债务的类型

| 类型 | 说明 | 示例 |
| :-- | :-- | :-- |
| 故意债务 | 明知不好但为了赶工期 | 跳过单元测试、硬编码配置 |
| 无意债务 | 不知道更好的方案 | 不合理的架构设计、过时的依赖 |
| 环境债务 | 外部环境变化导致 | 框架版本过旧、依赖库停止维护 |
| 代码债务 | 代码层面的问题 | 重复代码、过长方法、缺少文档 |

## 2. 技术债务识别

```java
// 识别信号
// 1. 代码层面
//    - SonarQube 报告的 Bug 和坏味道
//    - 测试覆盖率低于 60%
//    - 构建时间超过 10 分钟
//
// 2. 架构层面
//    - 添加新功能需要修改多处代码
//    - 模块间耦合严重
//    - 缺少自动化测试
//
// 3. 团队层面
//    - 新人上手需要超过 2 周
//    - 频繁出现"改了这里那里坏了"
//    - 团队不敢重构某些模块

// 技术债务登记模板
/**
 * 债务编号：TD-001
 * 债务名称：订单模块缺少单元测试
 * 债务类型：代码债务
 * 严重程度：高
 * 影响范围：订单模块所有功能
 * 产生原因：赶工期跳过了测试
 * 偿还成本：5 人天
 * 风险：每次发布都有回归 Bug
 * 优先级：P1
 * 计划偿还时间：下个 Sprint
 */
```

## 3. 技术债务管理策略

```java
// 策略 1：每次 Sprint 预留 20% 时间处理技术债务
// Sprint 容量：20 故事点
// 功能开发：16 点（80%）
// 技术债务：4 点（20%）

// 策略 2：Boy Scout Rule（离开时比来时更干净）
// 每次修改代码时，顺手改善周围的代码
// 不必专门安排时间，积少成多

// 策略 3：技术债务 Sprint
// 每 4-5 个功能 Sprint 后，安排一个专门的技术 Sprint
// 集中处理积累的技术债务

// 策略 4：重构与功能开发结合
// 在开发新功能时，顺便重构相关模块
// 避免"等有时间再重构"（永远不会有时间）
```

## 4. 技术债务的 ROI 分析

```java
// 偿还技术债务的收益计算
// 假设：订单模块缺少测试，每次发布平均有 2 个回归 Bug
// 每个 Bug 修复成本：2 小时（定位 + 修复 + 测试）
// 每月发布 4 次，每月损失：2 × 2 × 4 = 16 小时
// 偿还成本：5 人天 = 40 小时
// 回本周期：40 / 16 = 2.5 个月

// 决策：如果偿还成本 < 3 个月的损失，应该立即偿还
```

> **技术债务的核心**：技术债务不是坏事，就像金融债务一样，适度的债务可以帮助你快速发展。关键是"有意识地借债，有计划地偿还"。无意识的债务才是危险的。
