# 需求分析

> **核心问题**：如何将模糊的业务需求转化为清晰的技术需求？如何避免需求理解偏差？

## 1. 用户故事与验收标准

```java
// 用户故事格式：As a [role], I want [feature], so that [benefit]
// 验收标准（AC）：Given-When-Then 格式

// 示例：购物车功能
// 用户故事：
// 作为一个注册用户，我想要将商品加入购物车，以便稍后统一结算。
//
// 验收标准：
// AC1: 用户可以将商品加入购物车
//   Given 用户已登录且商品有库存
//   When  用户点击"加入购物车"
//   Then  购物车数量增加，显示成功提示
//
// AC2: 同一商品重复添加时合并数量
//   Given 购物车中已有商品 A（数量 2）
//   When  用户再次将商品 A 加入购物车（数量 1）
//   Then  购物车中商品 A 数量变为 3
//
// AC3: 库存不足时提示用户
//   Given 商品库存为 5，购物车中已有 4 件
//   When  用户再添加 2 件
//   Then  提示"库存不足，最多可添加 1 件"
```

## 2. 需求分解

```java
// 大需求分解为小需求（INVEST 原则）
// I - Independent（独立的）
// N - Negotiable（可协商的）
// V - Valuable（有价值的）
// E - Estimable（可估算的）
// S - Small（小的）
// T - Testable（可测试的）

// 示例：将"订单系统"分解为独立的用户故事
// 1. 创建订单（基础功能）
// 2. 查看订单列表
// 3. 查看订单详情
// 4. 取消订单
// 5. 订单支付
// 6. 订单退款
// 7. 订单物流跟踪
```

## 3. 需求评审 Checklist

```markdown
□ 需求目标是否明确？
□ 用户故事是否完整（角色-功能-价值）？
□ 验收标准是否清晰（Given-When-Then）？
□ 是否有边界条件和异常场景？
□ 是否有非功能需求（性能、安全）？
□ 是否有 UI/UX 设计稿？
□ 依赖的外部系统是否明确？
□ 技术可行性是否评估过？
□ 工期估算是否合理？
```

## 4. 需求变更管理

```java
// 需求变更流程
// 1. 提出变更请求（描述变更内容和原因）
// 2. 评估影响范围（工期、成本、风险）
// 3. 审批（PO/PM 决策）
// 4. 更新需求文档和 Sprint Backlog
// 5. 通知相关方

// 变更影响评估模板
/**
 * 变更名称：订单支持部分退款
 * 变更原因：用户反馈需要部分退款功能
 * 影响范围：
 *   - 后端：退款逻辑、金额计算
 *   - 前端：退款页面、退款记录
 *   - 测试：退款场景覆盖
 * 额外工期：3 天
 * 风险：与支付渠道的接口可能需要调整
 * 决策：同意变更，纳入下个 Sprint
 */
```

> **需求分析的核心**：好的需求分析不是记录用户说什么，而是理解用户要什么。用户说"我想要一匹更快的马"，实际需求是"更快的交通工具"。
