## 二、核心问题

### 问题 1：RabbitMQ / ES / Kafka 深度严重不足

这三个模块的平均篇幅只有 2-4KB，内容基本是：

- 一个标题
- 一个表格（属性/参数/对比）
- 一段代码示例
- 结束

**缺失**：

- 为什么这样设计？（设计动机）
- 底层原理是什么？（机制深挖）
- 什么场景用？什么场景不用？（适用性分析）
- 踩过什么坑？（实战经验）
- 和竞品/替代方案的取舍？（决策依据）

**对比**：MySQL 的 Buffer Pool 一章 11KB，从"一次随机读的代价"讲起，解释了 LRU 的分区策略、预读污染、全表扫描污染，有场景、有原理、有对策。RabbitMQ 的 Queue 基础只有 1.6KB，只列了属性表格和代码。

### 问题 2：MySQL 内部章节深，外围章节薄

MySQL 模块内部分化严重：

**深（10-27KB）**：

- InnoDB 内核（Buffer Pool、Redo Log、Undo Log、数据页）
- 事务与锁（MVCC、锁机制、死锁）
- 索引（B+树）

**薄（3-6KB）**：

- 基础入门（概览、字符集、SQL 规范）
- 高级特性（窗口函数、CTE、JSON、分区表、全文索引）
- 运维管理（备份、监控、安全、用户管理、连接管理）
- 复制与高可用（异步复制、GTID、组复制、读写分离）
- 扩展架构（分库分表、在线DDL、数据迁移、NewSQL）

### 问题 3：Redis 核心章节不错，但分布不均

**好（8-10KB）**：

- 缓存工程（穿透、击穿、雪崩、一致性、大Key）— 这是 Redis 最有特色的部分，写得深

**薄（3-6KB）**：

- 数据模型（基础类型、高级类型、对象编码）
- 单机核心（RDB、AOF、过期策略、淘汰策略）
- 高可用（主从复制、哨兵、集群）

### 问题 4：可读性差距——"参考手册式" vs "叙事式"

Java/Spring 的写法：

```text
从一个真实问题出发 → 为什么需要这个技术 → 底层怎么工作 → 边界在哪 → 怎么用好
```

RabbitMQ/ES/Kafka 的写法：

```text
标题 → 表格 → 代码 → 下一章
```

前者有"故事线"，读者跟着思路走；后者是"字典"，查得到但学不会。

### 问题 5：Elasticsearch 搜索章节名不副实

ES 的核心价值是搜索，但搜索章节（03-search）平均只有 2-3KB/篇。Query DSL 是 ES 最复杂的部分，当前内容只覆盖了 query vs filter 的基本概念，缺少：

- 各种查询类型的详细用法（match、term、range、bool、nested、parent-child）
- 评分机制（TF-IDF、BM25、自定义评分）
- 搜索结果处理（高亮、排序、分页策略）
- 性能优化（查询缓存、过滤器缓存、预热）

### 问题 6：Engineering 模块偏概念，缺实操

Engineering 模块的章节多是概念介绍（SOLID、架构风格、DDD 概览），缺少：

- 具体案例（"我们遇到了什么问题，用了什么原则解决"）
- 代码示例（重构前后对比）
- 决策框架（"什么时候用微服务，什么时候不用"）

## 四、解决方案方向

### 方向 A：按优先级逐模块补深度

从 P0 开始，逐模块将薄章节补充到 8-15KB/篇的目标深度。

**工作量估算**：

- RabbitMQ：~40 篇需要扩充，每篇补 5-10KB → 约 200-400KB 新增内容
- ES：~15 篇核心章节需要扩充 → 约 75-150KB
- Kafka：~10 篇需要扩充 → 约 50-100KB
- MySQL：~15 篇需要扩充 → 约 75-150KB
- Redis：~10 篇需要扩充 → 约 50-100KB

### 方向 B：统一写作风格

参考 MySQL InnoDB 内核和 Redis 缓存工程的写法，建立统一的内容标准：

1. **每章开头**：从一个真实问题或场景切入（不要直接上表格）
2. **原理部分**：解释"为什么"，不只是"是什么"
3. **代码示例**：完整可运行，不是伪代码片段
4. **边界与陷阱**：每章末尾加"踩坑提醒"或"适用边界"
5. **篇幅目标**：核心章节 8-15KB，基础章节 5-8KB

### 方向 C：按模块逐个处理

不急于一次性补完，按实际使用优先级逐个模块处理。每次处理一个模块，确保该模块整体质量达标后再进入下一个。

## 五、建议执行顺序

1. **RabbitMQ**（最薄，差距最大）
2. **Elasticsearch**（搜索核心是 ES 的灵魂，当前最弱）
3. **Kafka**（消息队列两篇对比，Kafka 深度也不够）
4. **MySQL 外围章节**（内核已经很好，补齐外围）
5. **Redis 单机核心和高可用**（缓存工程已经很好，补齐其他）
6. **Engineering + Design-pattern**（最后处理，优先级最低）
