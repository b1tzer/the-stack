# PE 加载过程：从文件到进程

前面的章节讲的是「文件」。这一章把 PE 格式串起来，看 Windows 加载器（Loader）如何把一个躺在硬盘上的 `.exe`，变成内存里正在运行的进程。理解加载过程，才能解释很多运行时现象，比如「为什么文件里的布局和内存里的布局不一样」「导入函数地址是什么时候确定的」。

## 1. 加载的整体流程

加载器启动一个 PE 文件，大致经历以下步骤：

```text
读取 PE 头 → 分配内存并映射节区 → 加载依赖 DLL
→ 解析导入表（填充 IAT）→ 处理重定位 → 执行 TLS 回调
→ 跳转到入口点（AddressOfEntryPoint）→ 程序开始运行
```

下面逐个环节说明。

## 2. 映射节区：文件布局 ≠ 内存布局

加载器先读 PE 头，按 `SizeOfImage` 在内存里预留一块区域，然后把各个节区「映射」进内存。

关键在于：**节区在文件里按 `FileAlignment`（如 `0x200`）对齐，映射进内存后按 `SectionAlignment`（如 `0x1000`）对齐**。所以同一个节区，在文件里的偏移和在内存里的 RVA 通常不相等——这正是上一章「文件偏移 ≠ RVA」的根源。

映射完成后，内存里的镜像就是「模块」（module），其起始地址就是模块基址（module base）。如果因为地址冲突或 ASLR，实际基址偏离了 `ImageBase`，加载器就按重定位表修正代码里的绝对地址。

## 3. 解析导入表：填充 IAT

映射完自己的节区后，加载器看导入表，逐项处理：

1. 对每个被依赖的 DLL，把它也加载进进程地址空间（如果还没加载）。
2. 对每个导入函数，找到它在对应 DLL 里的真实地址。
3. 把这些真实地址填入本模块的 **IAT（导入地址表）**。

这一步完成之前，程序的代码还不能调用导入函数（因为 IAT 里还没有有效地址）。填完之后，代码里 `call [IAT 中的地址]` 才能正确跳到系统函数。

这也是为什么静态分析时，导入函数的地址显示成「符号」；而动态分析时，IAT 里已经是真实地址。

## 4. 处理重定位：修正绝对地址

如果模块被加载到非首选基址，加载器遍历重定位表，把代码里所有写死的绝对地址统一加上「实际基址 - ImageBase」的偏移量。这样代码里引用全局变量、字符串、函数的绝对地址才指向正确位置。

ASLR 开启时，这一步每次都发生，所以每次运行的绝对地址都不同。

## 5. 执行 TLS 回调与跳转入口点

在跳转到真正的入口点之前，加载器会先执行 **TLS 回调函数**（如果存在）。这就是上一章说的「程序可以在 `main` 之前执行代码」的机制。

最后，加载器跳转到 `AddressOfEntryPoint` 指向的入口点。对 C/C++ 程序，这里通常是 CRT 初始化代码，再由它调用 `main`。从这里开始，程序进入「用户代码」的执行阶段。

## 6. 这条链路对逆向的意义

理解加载过程，能解释逆向中几个常见现象：

| 现象 | 解释 |
| :-- | :-- |
| 文件里和内存里的地址对不上 | 节区按不同粒度对齐，文件偏移 ≠ RVA |
| 导入函数地址在静态和动态里不同 | 静态是符号，加载时 IAT 才被填成真实地址 |
| 每次运行地址都变 | ASLR + 重定位修正 |
| 断点还没到入口点就有代码执行 | TLS 回调在入口点之前运行 |

这些现象背后的机制，正是理解后续动态调试、加壳脱壳的基础。
