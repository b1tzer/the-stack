# 异常处理机制

程序运行时会遇到错误——除零、访问违例、非法指令。Windows 通过异常处理机制来应对这些错误。逆向里，异常处理既是「理解程序如何容错」的钥匙，也是「识别反调试手段」的线索。

## 1. 什么是异常

异常是 CPU 或程序在运行时发出的「出错信号」。常见的几种：

| 异常 | 触发场景 |
| :-- | :-- |
| 访问违例（Access Violation） | 读写未映射或无权访问的内存 |
| 除零异常 | 整数除以 0 |
| 断点异常（`INT 3`） | 执行到 `0xCC`，调试器靠它下软件断点 |
| 单步异常 | 单步执行时每走一条指令触发一次 |
| 非法指令 | 执行了无效的机器码 |

注意，`INT 3` 断点异常和单步异常也走异常处理机制——这解释了为什么调试器能截获断点和单步，也解释了为什么程序能反过来利用异常检测调试器。

## 2. 两种历史机制：SEH 与表驱动

Windows 的异常处理有两种历史机制：

- **x86 的 SEH（Structured Exception Handling，结构化异常处理）**：在栈上维护一个异常处理链表（`fs:[0]` 指向链表头），每个 `try` 块对应链表上的一个节点。异常发生时，系统遍历链表找处理函数。
- **x64 的异常处理**：改为**基于表**。编译器在 `.pdata` 节里生成展开信息（unwind info），异常处理函数不再挂栈上链表，而是查表定位。

对逆向的实际影响：在 x64 反汇编里，你**不会再看到** x86 那种 `push handler; mov fs:[0], esp` 的经典 SEH 安装序列。如果看到程序手动操作异常处理、或故意触发异常来跳转，那是花指令或反调试的手段。

## 3. 异常如何被处理

以 x64 为例，异常发生时的处理流程大致是：

```text
异常发生 → CPU 查 IDT（中断描述符表）进入内核
→ 内核把异常分发给当前线程的异常处理链
→ 先看有没有调试器（调试器有优先处理权）
→ 没有调试器，或调试器不处理 → 查表找用户态异常处理函数
→ 找到就执行，找不到就终止进程
```

这里有个对逆向很关键的点：**调试器有异常处理的优先权**。程序抛出的异常，调试器先看到，可以选择「处理掉」或「转交给程序」。所以程序可以故意抛异常，试探「异常有没有被调试器截获」——这本身就是一个反调试信号。

## 4. 异常与反调试的关系

程序故意抛异常，是检测调试器的一种手段：

- 如果程序在调试器里运行，异常会被调试器截获，程序可能检测到「异常没有被正常处理」。
- 程序也可能自己安装异常处理函数，在函数里检查调试寄存器、检查是否有调试器痕迹。

所以，[反调试与反静态分析](../07-packing/chapter-03-virtualization-anti-debugging.md)里很多技巧都建立在异常机制上。理解异常如何被分发，才能理解这些反调试手段为什么有效、如何绕过。

## 5. 逆向中如何看异常处理

分析程序时，关注异常处理的几个角度：

- **看导入表**：程序导入了 `SetUnhandledExceptionFilter`、`AddVectoredExceptionHandler` 等，说明它主动安装了异常处理。
- **看 `.pdata` 节**：x64 程序的展开信息在这里，反汇编器据此还原 `try/catch` 结构。
- **警惕「异常驱动的控制流」**：如果程序故意抛异常、在异常处理函数里跳转到别处，这是混淆或反调试的信号。
