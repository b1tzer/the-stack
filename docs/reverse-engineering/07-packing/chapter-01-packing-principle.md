# 加壳原理与识别

程序保护的手段里，最「面」上的一层是壳（packer）。壳把整个程序打包、压缩甚至加密，让静态分析在最外层就碰壁。这一章讲壳是什么、怎么工作、如何识别。

## 1. 壳是什么，为什么要加

壳是包裹在原始程序外面的一层代码。加壳后，磁盘上的文件不再是原始程序，而是「壳 + 被壳处理过的原始程序数据」。它的用途有两类：

- **压缩**：减小文件体积（如 UPX、ASPack）。
- **保护**：让分析、修改、破解变难（如 VMProtect、Themida）。

两类目的常叠加。对逆向来说，壳是一个障碍：**加了壳的程序，你静态看到的几乎全是壳的代码，真正的逻辑被压缩/加密藏起来了。**

## 2. 壳的工作原理

不管哪种壳，运行时的基本流程都类似：

```text
启动 → 壳的入口（stub 解压/解密代码）
     → 在内存里还原出原始程序的代码和数据
     → 跳转到原始程序的真正入口点（OEP）
     → 原始程序正常执行
```

这里有个关键概念：**OEP（Original Entry Point，原始入口点）**。它是加壳前程序真正的入口点，被壳藏了起来。脱壳的目标，就是找到 OEP、把还原后的程序从内存里 dump 出来、并修复它的导入表。

理解这个「stub 先跑、还原、再跳 OEP」的流程，是理解一切脱壳方法的基础。

## 3. 识别壳

脱壳前先判断「加没加壳、加的什么壳」。几个信号（[静态分析基础](../05-static-analysis/chapter-01-basics.md)也提过）：

- **节区名异常**：如 UPX 的 `UPX0`、`UPX1`，或 `.packed`、`.vmp` 这类非标准名。
- **入口点异常**：入口点（entry point）不在 `.text` 节，而落在某个陌生的节区。
- **节区属性矛盾**：某个节的 `SizeOfRawData`（文件里的大小）远小于 `VirtualSize`（内存里的大小），说明「文件里很小、运行时却要展开」，是压缩壳的典型特征。
- **工具直接报告**：**Detect It Easy（DIE）** 会自动识别并报出壳名（如 "UPX(3.96)"）。

识别出壳的类型后，脱壳策略就清晰了：**有专用脱壳工具的优先用工具；没有的再手动脱。**

## 4. 常见壳：UPX 与它的同类

**UPX** 是最常见的开源压缩壳。它的特征是节区名为 `UPX0`、`UPX1`，且因为格式公开、自带还原信息，脱壳最简单——`upx -d target.exe` 一条命令即可。

其他常见的压缩壳还有 ASPack、FSG、MPRESS 等，原理与 UPX 类似：压缩代码段，运行时解压到内存，跳回 OEP。这类壳的脱壳难度不高，因为「壳总会把原程序完整还原出来」。

对比之下，[虚拟化保护](./chapter-03-virtualization-anti-debugging.md)和反调试手段则是另一个量级的难度。

## 5. 自动脱壳：优先用现成工具

很多常见壳有成熟的自动脱壳方案，优先使用：

- **UPX**：`upx -d target.exe`。
- **通用脱壳插件/脚本**：x64dbg 生态里有针对常见壳的脱壳脚本或插件，能自动完成「找 OEP → dump → 修 IAT」。
- **专用脱壳机**：针对某些老壳有独立脱壳工具。

自动脱壳的优点是快、不易出错。**先试自动，失败再手动**，是务实的顺序。自动脱壳失败通常是因为壳版本更新、或壳本身是「保护壳」而非「压缩壳」。
