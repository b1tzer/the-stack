# 授权验证与完整性校验

商业软件普遍有授权验证——序列号、许可证文件、在线激活——来限制未授权使用。同时用完整性校验防止程序被篡改。这一章讲这些机制**如何工作**，目的是理解程序行为、完成安全研究，而不是破解。

> 未经授权绕过商业软件的授权验证，在很多司法辖区违法或违反许可协议。本文只讲解机制原理，用于理解程序、分析恶意软件、在授权范围内做安全研究，不提供针对具体商业产品的破解步骤。

## 1. 常见授权验证机制

软件的授权验证，本质是回答一个问题：**「这个使用者，有没有合法授权」**。常见三种形态：

| 机制 | 原理 | 验证点 |
| :-- | :-- | :-- |
| 序列号 | 用户输入一串号，程序校验它是否符合规则 | 本地算法校验 |
| 许可证文件 | 授权信息写进文件（常加密/签名） | 本地读文件校验 |
| 在线激活 | 把授权信息发到服务器验证 | 网络 + 本地双重校验 |

三种机制的共同点：程序里有一个「校验函数」，输入授权信息，输出「通过 / 不通过」。逆向分析的目标，通常是理解这个校验函数**如何判断**。

## 2. 反汇编里定位授权逻辑

定位授权逻辑，有几个线索：

- **字符串**：搜 `license`、`serial`、`trial`、`activation`、`invalid key` 等字样。
- **导入函数**：`CryptVerifySignature`、哈希函数、`RegQueryValueEx`（读注册表里的授权信息）。
- **分支结构**：一个「判断通过/失败」的分支，通过后进入主功能，失败则退出或限制功能。

定位到校验函数后，分析它的逻辑：它读什么输入、做什么变换、和什么比较。这就还原了「授权如何被验证」。

## 3. 授权校验的常见实现

校验函数里常见的实现模式：

- **序列号算法**：把输入做变换（哈希、异或、位移），和硬编码值比较。特征：`xor`、循环、和常量比较。
- **数字签名验证**：用公钥验证许可证文件的签名。特征：`CryptVerifySignature`、导入证书/公钥。
- **特征码/机器码绑定**：授权和某台机器绑定（读硬件信息、算机器码）。特征：读 CPU 序列号、磁盘序列号、MAC 地址。

识别出校验用的是什么机制，就能理解「授权信息的真实性如何保证」——是简单的本地比较，还是密码学签名。

## 4. 完整性校验

程序还会校验「自己有没有被篡改」——防止被修改、打补丁、注入。

常见实现：

| 机制 | 原理 | 反汇编特征 |
| :-- | :-- | :-- |
| CRC/校验和 | 对代码段算校验和，和预期值比 | 对一段内存做循环异或/累加 |
| 哈希 | 对代码段算哈希（MD5/SHA） | 导入哈希函数，输入是代码段 |
| 数字签名 | 校验整个文件的 Authenticode 签名 | 系统级，或 `WinVerifyTrust` |

完整性校验对逆向的影响：**它让软件断点（会改代码）失效**——因为你改了一个字节，校验和就对不上了。这就是[反调试与反静态分析](../07-packing/chapter-03-virtualization-anti-debugging.md)里「自校验」的原理。

## 5. 分析与绕过的边界

理解授权和完整性机制后，逆向分析师要面对一个选择：是「分析理解」，还是「绕过」。

**分析理解**——理解机制如何工作，用于安全研究、兼容性分析、恶意软件分析，是正当用途。

**绕过**——让程序跳过授权校验、去除限制，未经授权属于破解，超出本文范围，也不应进行。

一个清晰的边界：**分析一个程序如何保护自己，是安全研究；破解它的保护，是侵权。** 本专题的定位，一直是前者。

## 6. 对恶意软件分析的借鉴

授权和完整性校验的技术，和恶意软件的反分析技术高度重合（自校验、反调试、加密）。因此，理解这些机制，对分析恶意软件同样有用：

- 恶意软件用完整性校验检测「是否被分析者改过」。
- 恶意软件用加密和混淆保护自己的配置和 C2 通信。

这些技术在本文和[反调试与反静态分析](../07-packing/chapter-03-virtualization-anti-debugging.md)里是相通的。

## 7. 完整实例：分析一个序列号校验

用一个「校验和」型序列号校验，走一遍授权逻辑的分析。目标程序的核心函数：

```c
int check_serial(const char* s) {
    int sum = 0;
    for (int i = 0; s[i]; i++) {
        sum += s[i];
    }
    return sum == 0x2A5;   // 校验和等于 677 才通过
}
```

**第一步：定位校验函数。** 搜字符串 `"serial"`、`"invalid key"` 之类的提示，或用交叉引用追到「判断通过/失败」的分支，向上找到 `check_serial`。

**第二步：还原算法。** 反编译或读反汇编，看到核心是一个累加循环，末尾和常量比较：

```asm
xor  eax, eax            ; sum = 0
loop:
movsx ecx, byte ptr [rdx] ; 读一个字符
test  ecx, ecx
je    check_sum          ; 字符串结束，去比较
add   eax, ecx           ; sum += c
inc   rdx
jmp   loop
check_sum:
cmp   eax, 0x2A5         ; sum == 677 ?
sete  al                 ; 返回比较结果
ret
```

**第三步：反推结论。** 算法是「所有字符 ASCII 码相加，和等于 677」。这意味着：**任何 ASCII 和等于 677 的字符串都能通过校验**（例如某个特定串），不需要精确还原出「唯一序列号」。

这个例子揭示了分析授权逻辑时的关键判断：**看清校验是「精确匹配」还是「弱校验」。** 校验和、固定 XOR、长度判断这类弱校验，往往有无数个有效输入；而数字签名、在线验证这类强校验，才真正难以绕过。理解校验的强度，是判断「这个授权保护有多可靠」的核心。

> 再次强调：本文分析的是自己编写的示例程序。对真实商业软件做同样的事，未经授权属于破解，不在本专题范围内。
