# 调试器的断点与单步机制

静态分析看的是代码写了什么，但回答不了运行起来真实发生了什么——尤其当程序有加密、压缩、动态生成代码时。本文讲动态分析的底层机制，是 [x64dbg](./chapter-02-x64dbg.md) 上手的理论准备：三类断点的原理和代价、单步执行的机制，以及调试器能看到什么、看不到什么。

## 1. 调试器怎么「控制」一个程序

调试器通过操作系统的**调试接口**接管目标进程。Windows 上，调试器启动或附加（attach）到目标进程后，两者建立一种特殊关系：目标进程每发生一次调试事件（断点命中、异常、模块加载、线程创建等），都会被**暂停**，并把事件报告给调试器；调试器处理后，再让目标进程继续运行。

调试器内部就是一个「等待事件 → 处理事件 → 继续运行」的循环（对应 Windows API 的 `WaitForDebugEvent` / `ContinueDebugEvent`）。你看到的「程序停在某行、单步走一步、继续跑」，本质都是这个循环在反复执行。

## 2. 软件断点：把指令临时换成 INT 3 {#software-breakpoint}

最常用的断点是**软件断点**。它的原理是：调试器把目标地址处那条指令的第一个字节，临时替换成 `0xCC`——即 `INT 3`（中断 3）指令。CPU 执行到这里时触发断点异常，控制权交回调试器；调试器再把原始字节恢复，让你看到程序停在了这里。

这解释了软件断点的几个特性：

- **成本几乎为零**，可以下任意多个。
- 它**修改了代码**（哪怕只是临时、且调试器负责恢复），所以对「校验自身代码完整性」的程序会失效或暴露——这是[反调试与反静态分析](../07-packing/chapter-03-virtualization-anti-debugging.md)的基础之一。
- 断点必须打在**指令边界**上。打在指令中间，替换的 `0xCC` 会被当成合法指令的一部分，程序直接跑飞或崩溃。

## 3. 硬件断点：不碰代码，但有数量上限 {#hardware-breakpoint}

硬件断点利用 CPU 专门的**调试寄存器**（x64 上的 `DR0`～`DR3` 存地址，`DR7` 控制模式），不修改任何代码。CPU 在执行或访问到这些地址时，硬件直接触发异常。

它的优点和限制都很鲜明：

- **优点**：不修改代码，程序很难察觉；不仅能断「执行」，还能断「读」或「写」某块内存（这是软件断点做不到的）。
- **限制**：**最多同时 4 个**（对应 DR0～DR3 四个寄存器）。

实际使用中，当你需要「监视某个变量何时被写入」、或「断点打在会被自校验的代码上」时，硬件断点是更合适的选择。

## 4. 内存断点：靠页保护来拦截访问 {#memory-breakpoint}

内存断点用于「当程序读写某块内存时停下」。它不靠 CPU 调试寄存器，而是靠**内存页保护**：调试器把目标内存所在页标记为 `PAGE_GUARD`（保护页），程序一旦访问该页，CPU 触发保护异常，调试器截获后判断「是不是访问了关心的地址」。

代价是：它以**页**（4 KB）为粒度，一个页被保护后，页内任何地址被访问都会触发，命中率「过宽」。实际调试器会在触发后检查具体地址，再决定是否放行。

三类断点各有适用场景，汇总如下：

| 断点类型 | 原理 | 数量上限 | 是否改代码 | 典型用途 |
| :-- | :-- | :-- | :-- | :-- |
| 软件断点 | 替换为 `INT 3` | 无限 | 是 | 在指定指令处停下 |
| 硬件断点 | 调试寄存器 | 4 个 | 否 | 监视内存读写、防自校验 |
| 内存断点 | 页保护 | 与页相关 | 否 | 拦截对某块内存的访问 |

## 5. 单步执行：一条一条地走

单步执行让程序一次只执行一条指令，然后停下。它的原理是设置 `RFLAGS` 的 **TF（Trap Flag，陷阱标志）位**：该位置位后，CPU 每执行完一条指令就触发一次调试异常，调试器借机停下。

单步执行适合精读关键代码，但很慢，不适合长距离跟踪。实际工作流是「**先跑到关键处下断点，再用单步精读附近几行**」——断点负责「跳过去」，单步负责「看清楚」。

## 6. 调试器能看到什么

暂停下来后，调试器展示的是目标进程此刻的完整状态，你能查看：

- **寄存器**：包括通用寄存器、RIP（当前执行位置）、RFLAGS 等。
- **内存**：任意合法地址处的字节，用内存视图查看或搜索。
- **栈**：当前调用链（调用栈/回溯），能看到「谁调用了谁」。
- **模块**：已加载的所有模块及其基址。

这些信息里，**调用栈**和**寄存器**是动态分析的两大抓手：调用栈告诉你执行到哪了、经过哪些函数；寄存器告诉你参数和中间值。结合静态分析得到的地图，你就能验证「这段代码是否真的被执行」「这个分支实际走没走」。

## 7. 动态分析的局限

动态分析很强，但有明确边界，需要心里有数：

- **只看得到执行到的路径**：程序没走到的分支，你观察不到。所以动态分析验证的是「这条路径上发生了什么」，而不是「整个程序能做什么」。
- **调试可能被察觉**：程序可以用反调试手段检测到调试器并改变行为或退出（[反调试与反静态分析](../07-packing/chapter-03-virtualization-anti-debugging.md)）。
- **调试恶意软件需要隔离环境**：让恶意程序在调试器里「真的跑起来」，意味着它可能真的联网、写文件、加密磁盘。务必在虚拟机或隔离环境里做（见[实战案例](../09-comprehensive-practice/chapter-01-crackme.md)的提醒）。

这就是为什么成熟的分析流程是**静态 + 动态交替**：静态画地图、动态验路径，两者互相补齐对方的盲区。
