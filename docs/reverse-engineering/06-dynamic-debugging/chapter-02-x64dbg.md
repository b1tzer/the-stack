# x64dbg 动态调试实操

> 上一篇讲了断点和单步的原理，这一篇把它们落到 x64dbg——Windows 用户态调试的事实标准，免费开源，是动态分析的主战场。

**前置条件**：已读 [调试器的断点与单步机制](./chapter-01-debugging-basics.md)，理解软件断点、硬件断点、单步的含义；电脑上装好 x64dbg（本文以 2025 年的版本为准，界面和快捷键长期稳定）。练手目标用[编译篇的 crackme.c](../01-program-basics/chapter-01-c-cpp-compilation.md)——一个读输入、校验、打印对错的小程序。

## 1. 安装与启动

x64dbg 是免安装的：从 [x64dbg.com](https://x64dbg.com/) 下载 snapshot 压缩包，解压后双击 `x96dbg.exe` 启动，它会让你选择启动 32 位（`x32dbg`）还是 64 位（`x64dbg`）调试器。分析 64 位程序选 **x64dbg**，分析 32 位程序选 x32dbg——用错位数会直接无法加载。

打开后是空的工作区。用 `File → Open`（或按 `F3`）选择你的 `.exe`，程序会被加载并停在**系统断点**（entry breakpoint）处，通常位于 `ntdll.dll` 里，还没到你的代码。

## 2. 认识 CPU 窗口

x64dbg 的核心是 **CPU 窗口**，它由四个面板组成，各有明确分工：

| 面板 | 位置 | 内容 |
| :-- | :-- | :-- |
| 反汇编 | 左上 | 当前地址附近的反汇编，最常用 |
| 寄存器 | 右上 | 各寄存器的值，可双击修改 |
| 内存 dump | 左下 | 某块内存的十六进制内容 |
| 栈 | 右下 | 当前线程的栈，含调用返回地址 |

几个高频快捷键先记住：`F9` 运行、`F12` 暂停、`F7` 单步步入（进入函数）、`F8` 单步步过（跳过函数）、`F2` 切换断点、`Ctrl+G` 跳转到地址、`Ctrl+F2` 重启程序。

## 3. 下断点，跑到关键处

先在反汇编面板跳到你想停的位置（`Ctrl+G` 输入地址或函数名，如 `main` 或 `&"Wrong password"` 所在逻辑），然后按 `F2` 在该行下断点——该行会变红。按 `F9` 运行，程序跑到断点处自动停下。

一个定位关键点的实用技巧：如果程序里有一段「正确密码」的判断，你可以先用字符串搜索（反汇编面板右键 `Search for → String references`，或 `Ctrl+F`）找到 `"Wrong password"` 字符串的位置，`Ctrl+G` 跳到引用它的比较指令附近，在那里下断点。

停到断点后，寄存器面板里 **RIP** 就是当前指令地址。此时你已经站在「程序运行到这一瞬间」的现场，可以开始观察。

## 4. 单步跟踪，观察分支

停在比较指令附近后，用单步看清楚程序走哪条分支：

- `F7`（步入）：执行一条指令，如果该指令是 `call`，会**进入**被调函数内部。
- `F8`（步过）：执行一条指令，如果该指令是 `call`，会**执行完整个函数**再停到下一行。

对「观察这段逻辑走哪条分支」来说，多用 `F8` 跳过不关心的函数调用，只在想深入某个函数时才用 `F7`。每走一步，观察寄存器面板的变化，尤其是 `RAX`（常是返回值）和标志位（决定条件跳转）。

走到 `cmp ... / jne ...` 这类指令时，留意反汇编面板右侧的跳转提示：x64dbg 会在跳转目标旁标注箭头，命中与否一目了然。

## 5. 查看和修改内存、寄存器

调试的核心动作之一，是看内存里的数据。在内存 dump 面板，`Ctrl+G` 输入地址即可跳转查看。要「跟着某个寄存器指向的内存看」，右键该寄存器选「Follow in Dump」即可把 dump 面板切到那个地址。

寄存器可以**直接双击修改**，用于改变执行走向（比如把标志位改掉让条件跳转反着走）。但更持久、更实用的修改方式是**打补丁**，见下一节。

## 6. 打补丁：直接改机器码 {#patching}

「打补丁」指的是直接修改程序在内存（进而可写回文件）里的机器码，改变程序行为。典型场景：把「校验失败跳走」改成「永远判定成功」。

操作步骤：

1. 在反汇编面板选中要改的指令（比如那条 `jne`），按**空格键**，输入新的汇编指令（如 `je` 或 `nop`）。
2. x64dbg 会提示「汇编后字节数可能变化」，确认后该指令被替换。
3. 按 `F9` 继续运行，观察程序行为是否如预期改变。

修改只影响当前内存。若要**永久保存到文件**，用 `File → Patch file`（或右键 `Patches`），x64dbg 会把改动写回磁盘生成新的 `.exe`。

> 补丁是逆向学习里「验证理解」的极好手段：你以为某个跳转是关键，就把它改掉，看程序行为是否按你的预期变化。改对了，说明你读懂了；改错了，说明判断有偏差，回去重新读。这只应作用于你自编的练手程序或授权目标。

## 7. 硬件断点与内存断点

[调试器的断点与单步机制](./chapter-01-debugging-basics.md)讲过三类断点的区别。x64dbg 里它们分别这样下：

- **软件断点**：反汇编面板按 `F2`。
- **硬件断点**：`Debug → Hardware breakpoints`，或在寄存器面板下方查看；可设执行/读/写，最多 4 个。
- **内存断点**：在内存 dump 面板选中一段内存，右键 `Breakpoint → Memory, Access/Write`。

需要「监视某变量何时被改写」时用内存/硬件写断点；断点总被程序莫名清掉（可能是自校验）时，改用硬件断点。

## 8. 条件断点与 API 断点

普通断点一命就停，但很多场景需要更精细的控制。两种进阶断点解决这个问题。

### 8.1 条件断点：满足条件才停

条件断点给断点加一个「命中条件」，只有条件为真才停下。典型场景：

- 循环执行 1000 次，只想在第 500 次停下。
- 只想在某个参数等于特定值时停下。

x64dbg 下条件断点：在断点上右键 → `Edit breakpoint`（或 `Breakpoint` 面板），在条件框里写表达式，例如：

```text
eax == 0x100    ; EAX 等于 0x100 才停
ecx > 10        ; ECX 大于 10 才停
```

命中条件不满足时，断点会「透明地」放行，程序继续跑。这样你能在「海量调用里精准抓到一次感兴趣的调用」，而不是手动按几百次 `F9`。

### 8.2 API 断点：在系统函数上停

API 断点是「在 Windows API 函数上下断点」。程序要读写文件、联网、查注册表，最终都要调用对应的系统函数，在这些函数上断点，就能在「程序做某类操作」的瞬间停下来。

x64dbg 下 API 断点：在命令栏输入 API 名，例如：

```text
bp CreateFileW     ; 在创建文件时停下
bp send            ; 在发送网络数据时停下
bp RegSetValueExW  ; 在写注册表时停下
```

命中后，看寄存器和栈就能拿到参数——`CreateFileW` 的第一个参数（RCX）是文件名，`send` 的缓冲区参数是要发送的数据。

API 断点的价值：**你不必先找到程序里调用它的位置，直接按行为下断点**。想追踪「程序打开了哪些文件」，断 `CreateFileW`；想追踪「发了什么数据」，断 `send`。这是从「行为」角度切入动态分析的最快方式。

### 8.3 什么时候用哪种

| 场景 | 用哪种 |
| :-- | :-- |
| 循环里只断特定迭代 | 条件断点 |
| 只断特定参数值 | 条件断点 |
| 追踪文件/网络/注册表操作 | API 断点 |
| 监视变量被改写 | 硬件/内存断点（上一节） |

## 9. 失败与回退

- **程序加载后直接退出或异常**：可能程序检测到调试器（[反调试与反静态分析](../07-packing/chapter-03-virtualization-anti-debugging.md)），或位数选错。先确认用的是 x64dbg 还是 x32dbg。
- **断点不命中**：检查是否打在指令中间，或该路径根本没被执行。
- **改乱指令想重来**：`Ctrl+F2` 重启程序，内存里的临时修改会还原；若已写回文件，重新用原始 `.exe` 打开。
- **栈/寄存器面板看不懂**：回到[调试器的断点与单步机制](./chapter-01-debugging-basics.md)，对照「寄存器、内存、调用栈」的含义。
