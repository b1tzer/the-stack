# 监控告警

> 监控是运维的「眼睛」。完善的监控体系能在故障发生前预警，在故障发生后提供定位依据。本章讲解监控维度、关键指标与告警阈值。

## 1. 监控维度

Redis 监控从三个维度构建：

| 维度 | 内容 |
| :-- | :-- |
| 服务端 | 操作系统层面：CPU、内存、网络、磁盘 |
| 应用端 | Redis 自身：QPS、延迟、内存、连接、命中率 |
| 联合分析 | 服务端与应用端数据交叉定位问题 |

```text
服务端（OS）     应用端（Redis）      联合分析
CPU / 内存    →  QPS / 延迟      →  定位根因
网络 / 磁盘   →  内存 / 命中率    →  关联证据
```

## 2. 关键指标

| 指标 | 含义 | 重要性 |
| :-- | :-- | :-- |
| QPS | 每秒请求数 | 高（吞吐基线） |
| 延迟 | 命令响应时间 | 高（用户体验） |
| 内存使用率 | used_memory / maxmemory | 高（OOM 风险） |
| 碎片率 | mem_fragmentation_ratio | 中（内存浪费） |
| 命中率 | keyspace 命中比例 | 中（缓存效果） |
| fork 耗时 | latest_fork_usec | 中（fork 停顿） |
| 连接数 | 当前连接数 | 中（连接耗尽） |
| 复制延迟 | 主从 offset 差 | 中（数据不一致） |

```bash
INFO stats       # QPS、命中率
INFO memory      # 内存、碎片率
INFO replication # 复制延迟
INFO clients     # 连接数
```

## 3. 告警阈值

| 指标 | 告警阈值（参考） | 说明 |
| :-- | :-- | :-- |
| 内存使用率 | > 80% | 接近上限，需扩容或淘汰 |
| 碎片率 | > 1.5 | 碎片较多，考虑整理 |
| 慢查询数量 | 持续增长 | 存在慢命令 |
| fork 耗时 | > 1 秒 | fork 停顿明显 |
| 连接数 | > 80% maxclients | 连接接近上限 |
| 命中率 | 显著下降 | 缓存失效或穿透 |

> 阈值需结合业务实际情况调整。告警的黄金法则是「宁可在故障前预警，不要在故障后才知道」。

## 4. 可视化方案

| 方案 | 说明 |
| :-- | :-- |
| CacheCloud | 搜狐开源的 Redis 私有云平台，一站式管理 |
| Prometheus + Grafana | 通过 redis_exporter 采集指标，Grafana 可视化 |
| 云厂商监控 | 各云厂商自带 Redis 监控面板 |
| 自建采集 | 定时执行 INFO，上报到自研监控平台 |

选择建议：中小团队用云厂商自带监控或 Prometheus + Grafana；需要多实例统一管理、权限控制等能力时考虑 CacheCloud 这类平台。
