# 主从复制

> 单机 Redis 存在单点故障与读写瓶颈。主从复制让数据在多个节点间同步，是哨兵与集群的基石。本章讲解主从复制的同步流程、读写分离与局限。

## 1. 为什么需要主从复制

单机 Redis 面临三个问题：

| 问题 | 说明 |
| :-- | :-- |
| 单点故障 | 主节点宕机，服务不可用 |
| 读瓶颈 | 所有请求都压在一个节点上 |
| 容量受限 | 单机内存有上限 |

主从复制引入「一主多从」结构：主节点负责写，从节点复制数据并分担读请求。

![主从复制一主多从架构](/redis/04-high-availability-chapter-01-replication-1.svg)

## 2. 同步流程

主从同步使用 `PSYNC` 命令，分为全量同步与增量同步。

### 2.1 全量同步

首次连接时，从节点复制主节点的全部数据：

![主从全量同步流程](/redis/04-high-availability-chapter-01-replication-2.svg)

全量同步步骤：

1. 从节点发送 `PSYNC`，主节点 BGSAVE 生成 RDB 快照
2. 主节点把 RDB 发送给从节点，从节点加载
3. 加载期间主节点的写命令进入复制缓冲区
4. RDB 加载完后，主节点把缓冲区的增量命令发给从节点

### 2.2 增量同步

断线重连后，只同步断开期间的增量数据。主从各自维护一个「复制偏移量」和「复制积压缓冲区（repl_backlog）」：

| 概念 | 说明 |
| :-- | :-- |
| 复制偏移量 | 记录已复制了多少字节数据 |
| 积压缓冲区 | 主节点保存最近一段写命令的环形缓冲 |

重连时从节点带上自己的偏移量，若该偏移量还在积压缓冲区范围内，就只补发缺失部分；否则需要全量同步。

## 3. 读写分离与异步复制

### 3.1 读写分离

主节点写、从节点读，把读请求分摊到从节点：

```bash
# 从节点配置
replicaof 主节点IP 6379      # 指定主节点
replica-read-only yes        # 从节点只读
```

### 3.2 异步复制

Redis 的复制是**异步**的：主节点写完就返回，不等待从节点确认。这意味着主从之间存在短暂的数据不一致。

| 特性 | 说明 |
| :-- | :-- |
| 高性能 | 主节点不等待从节点，写入延迟低 |
| 可能丢数据 | 主节点宕机时，未同步的数据丢失 |
| 弱一致 | 读从节点可能读到旧数据 |

> 异步复制决定了「主从 + 读写分离」无法提供强一致。如果业务要求读到的数据必须是最新的，就不能把读请求分流到从节点。

## 4. 局限

主从复制解决了「读扩展」与「数据冗余」，但仍有明显局限：

| 局限 | 说明 |
| :-- | :-- |
| 无法自动故障转移 | 主节点宕机需手动切换，服务中断 |
| 写无法扩展 | 写仍只在主节点，写瓶颈未解决 |
| 可能脑裂 | 主从网络分区时，可能出现多个主节点 |

主从复制无法自动故障转移的问题，由哨兵（第 2 章）解决；写无法水平扩展的问题，由集群（第 3 章）解决。
