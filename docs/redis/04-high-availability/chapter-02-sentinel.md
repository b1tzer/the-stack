# 哨兵模式

> 主从复制需要手动切换主节点，哨兵（Sentinel）补上了「自动故障转移」这一环。本章讲解哨兵的职责、故障转移流程与局限。

## 1. 三件职责

哨兵是一个独立的进程，负责监控主从节点，并在主节点故障时自动完成切换。

![哨兵集群监控架构](/redis/04-high-availability-chapter-02-sentinel-1.svg)

哨兵的三件职责：

| 职责 | 说明 |
| :-- | :-- |
| 监控 | 周期性检测主从节点是否存活 |
| 通知 | 节点故障时通知管理员或其他程序 |
| 自动故障转移 | 主节点故障时，选新主并让其他从节点跟随 |

## 2. 故障转移流程

故障转移分为四个阶段：

![哨兵故障转移流程](/redis/04-high-availability-chapter-02-sentinel-2.svg)

### 2.1 主观下线与客观下线

| 阶段 | 说明 |
| :-- | :-- |
| 主观下线（SDOWN） | 单个哨兵发现主节点超时无响应，主观认为下线 |
| 客观下线（ODOWN） | 多个哨兵（达到 quorum）都认为主节点下线，客观确认 |

单个哨兵判断下线可能是误判（网络抖动），多个哨兵达成一致才可靠。

### 2.2 选举领头哨兵

客观下线后，哨兵之间通过类 Raft 的共识算法选举出一个「领头哨兵」，由它负责执行故障转移。

### 2.3 执行故障转移

领头哨兵按优先级从「从节点」中选出新主节点：

1. 过滤掉不健康的从节点（下线、断连）
2. 按 `slave-priority` 优先级选最高的
3. 优先级相同时，选复制偏移量最大的（数据最新）
4. 都相同时，选 runid 最小的

选出新主后，领头哨兵让其他从节点复制新主，并把原主节点降级为从节点（待其恢复后重新加入）。

## 3. 配置

```bash
# sentinel.conf
sentinel monitor mymaster 127.0.0.1 6379 2   # 监控主节点，quorum=2
sentinel down-after-milliseconds mymaster 30000  # 30 秒无响应判下线
sentinel failover-timeout mymaster 180000        # 故障转移超时
```

| 配置 | 含义 |
| :-- | :-- |
| `monitor` | 指定监控的主节点与 quorum（法定人数） |
| `down-after-milliseconds` | 判定下线的时间阈值 |
| `failover-timeout` | 故障转移的超时时间 |

> quorum 是「判定客观下线所需的最少哨兵数」，与「执行转移的哨兵数」是两个概念。哨兵数量一般建议 ≥ 3，且为奇数，避免脑裂时无法达成多数。

## 4. 局限

哨兵解决了「自动故障转移」，但仍有局限：

| 局限 | 说明 |
| :-- | :-- |
| 容量受限 | 所有节点存全量数据，写仍只能在主节点 |
| 无法水平扩展 | 数据量大时单主内存不够，哨兵无法分片 |
| 切换有窗口 | 故障转移期间短暂不可写 |

哨兵解决「高可用」，集群解决「水平扩展」。数据量大到单机装不下时，就要用集群（第 3 章）。
