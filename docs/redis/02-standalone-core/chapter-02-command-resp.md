# 命令执行与 RESP

> 一条 `SET key value` 从客户端发出到 Redis 返回 `OK`，中间经历了协议编码、网络传输、协议解析、命令查找、执行、响应写回。理解这条链路，才能解释命令是如何被可靠、高效地执行的。

## 1. RESP 协议

RESP（REdis Serialization Protocol）是客户端与 Redis 通信的协议。它简单、易解析、二进制安全。

### 1.1 五种数据类型

| 类型 | 首字节 | 含义 | 示例 |
| :-- | :-- | :-- | :-- |
| 简单字符串 | `+` | 简单回复 | `+OK\r\n` |
| 错误 | `-` | 错误信息 | `-ERR unknown command\r\n` |
| 整数 | `:` | 整数回复 | `:1000\r\n` |
| 批量字符串 | `$` | 二进制安全的字符串 | `$3\r\nfoo\r\n` |
| 数组 | `*` | 多个元素 | `*2\r\n$3\r\nfoo\r\n$3\r\nbar\r\n` |

### 1.2 命令编码格式

客户端把命令编码为「数组 + 批量字符串」的格式发给 Redis：

```txt
客户端发送：SET mykey myvalue
实际字节流：*3\r\n$3\r\nSET\r\n$5\r\nmykey\r\n$7\r\nmyvalue\r\n
             ↑        ↑            ↑              ↑
             数组3     SET(长度3)    mykey(长度5)    myvalue(长度7)
```

- `*3`：这是一个包含 3 个元素的数组
- `$3\r\nSET\r\n`：第一个元素是长度 3 的字符串 "SET"
- 依次类推

### 1.3 内联命令

除了 RESP 格式，Redis 也支持内联命令（空格分隔的纯文本），例如直接发送 `PING`。这只用于 telnet 等手工调试场景，客户端库一般都用 RESP 格式。

### 1.4 RESP3（Redis 6.0+）

RESP2 只有 5 种类型，RESP3 新增了更多类型：

| 新增类型 | 首字节 | 说明 |
| :-- | :-- | :-- |
| 双精度浮点 | `,` | 浮点数 |
| 布尔 | `#` | true/false |
| 空值 | `_` | NULL |
| Blob 错误 | `!` | 带长度的错误信息 |
| Map | `%` | 键值对映射 |
| Set | `~` | 集合类型 |

```bash
# 启用 RESP3
HELLO 3
```

RESP3 的价值在于更丰富的类型系统，客户端可以更精确地反序列化响应，减少类型转换。

## 2. 命令解析

Redis 收到网络字节流后，需要把它解析成内部可执行的命令结构。

解析流程：

![RESP 命令解析流程](/redis/02-standalone-core-chapter-02-command-resp-1.svg)

解析的关键点：

| 环节 | 说明 |
| :-- | :-- |
| 读缓冲区 | 客户端连接有一个输入缓冲区（默认 1GB），读到的字节先暂存于此 |
| 协议判断 | 首字节是 `*` 走 RESP 多批量命令解析，否则走内联命令解析 |
| 参数数组 | 解析出 `argv`（参数数组）与 `argc`（参数个数） |
| 二进制安全 | 批量字符串按 `$长度` 精确读取，不依赖 `\0` 结尾 |

### 2.1 客户端输入缓冲区

每个客户端连接都有一个输入缓冲区（`querybuf`），用于暂存从网络读到的数据：

```bash
# 查看客户端缓冲区
redis-cli CLIENT LIST
# qbuf=1024 qbuf-free=32678 ...
```

| 字段 | 含义 |
| :-- | :-- |
| `qbuf` | 已使用的缓冲区大小 |
| `qbuf-free` | 剩余可用空间 |

> 输入缓冲区过大会占用大量内存。如果某个客户端发送了超大命令（如 `KEYS *` 返回百万个 key），可能导致内存飙升。生产环境建议设置 `client-query-buffer-limit` 限制单个客户端缓冲区大小。

## 3. 命令表查找

解析出命令名后，Redis 需要找到对应的命令实现。它维护一个命令表——所有命令的哈希表。

```txt
命令表（哈希表，O(1) 查找）
  "SET"   → redisCommand { 实现函数, 参数个数, 属性标志 }
  "GET"   → redisCommand { ... }
  "HSET"  → redisCommand { ... }
  ...
```

`redisCommand` 结构的关键字段：

| 字段 | 作用 |
| :-- | :-- |
| `proc` | 实现函数指针，指向真正执行命令的 C 函数 |
| `arity` | 参数个数，正数=精确，负数=最小参数数 |
| `flags` | 命令属性（写命令/只读命令/管理命令等） |
| `microseconds` | 累计执行耗时（用于慢查询统计） |
| `calls` | 累计调用次数 |

查找特点：

- **O(1) 哈希查找**：命令名作为 key，哈希表直接命中
- **大小写不敏感**：命令名统一转小写后查找，`SET` 与 `set` 等价
- **未知命令报错**：找不到返回 `-ERR unknown command`

## 4. 执行流程与钩子

找到命令后，执行过程会经过一系列钩子（Hook），这些钩子承载了 Redis 的很多附加能力。

![命令执行流程](/redis/02-standalone-core-chapter-02-command-resp-2.svg)

执行流程各环节：

| 环节 | 说明 |
| :-- | :-- |
| 参数校验 | 检查参数个数是否符合 arity 要求 |
| 键过期检查 | 惰性删除：访问到已过期 Key 时先删除再执行 |
| 执行命令 | 调用命令对应的实现函数，操作数据结构 |
| 慢查询日志 | 记录执行耗时超过阈值的命令 |
| AOF 传播 | 写命令追加到 AOF 缓冲区（见 [持久化](./chapter-05-persistence.md)） |
| 复制传播 | 写命令同步给从库（见 [主从复制](../04-high-availability/chapter-01-replication.md)） |
| 返回响应 | 把结果编码为 RESP 格式写回客户端 |

> 钩子机制的价值：Redis 把「持久化」「复制」等能力通过钩子挂在命令执行链路上，任何写命令都会自动触发 AOF 追加与主从传播，无需命令实现自己操心。这是 Redis 架构简洁的关键设计之一。

## 5. 慢查询日志 {#slowlog}

慢查询日志记录执行时间超过阈值的命令，是排查性能问题的第一手资料。

```bash
# 配置
slowlog-log-slower-than 10000   # 超过 10ms 记录（微秒）
slowlog-max-len 128             # 最多保存 128 条

# 查看
SLOWLOG GET 10                  # 获取最近 10 条慢查询
SLOWLOG LEN                     # 慢查询总数
SLOWLOG RESET                   # 清空
```

慢查询日志输出示例：

```txt
1) 1) (integer) 1           # 日志 ID
   2) (integer) 1712500000  # 时间戳
   3) (integer) 15000       # 耗时（微秒）
   4) 1) "KEYS"             # 命令
      2) "*"
   5) "127.0.0.1:54321"     # 客户端地址
   6) ""                    # 客户端名称
```

| 常见慢命令 | 原因 | 替代方案 |
| :-- | :-- | :-- |
| `KEYS *` | 遍历所有 key，O(n) | `SCAN` 分批迭代 |
| `HGETALL` | 大 Hash 全量获取 | `HSCAN` 或只取需要的字段 |
| `SMEMBERS` | 大 Set 全量获取 | `SSCAN` 分批迭代 |
| `DEL` 大 Key | 同步删除阻塞 | `UNLINK` 异步删除 |
| `SORT` | 排序开销大 | 业务层排序或用有序集合 |

> 慢查询日志是排查性能问题的第一步。如果发现慢命令，优先用替代方案；如果没有替代方案，考虑拆分数据或异步处理。
