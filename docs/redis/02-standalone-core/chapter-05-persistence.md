# 持久化 RDB 与 AOF 

> Redis 的数据都在内存里，一旦宕机就全部丢失。持久化把内存数据写到磁盘：RDB 用「快照」整体序列化，AOF 用「追加命令日志」逐条记录，混合持久化则二者结合。本章讲解三种方案的原理、取舍与生产选型。

## 1. RDB

### 1.1 工作原理

RDB 把某个时刻的内存数据整体序列化成一个二进制文件（默认 `dump.rdb`），恢复时直接把这个文件加载回内存。

![RDB 快照与恢复](/redis/02-standalone-core-chapter-05-persistence-1.svg)

恢复时，Redis 启动检测到 `dump.rdb` 后由主线程加载：加载期间不接收任何命令，文件越大恢复耗时越长。RDB 恢复比 AOF 重放快（直接读二进制、无需逐条执行命令），但并非零延迟——一个数 GB 的快照恢复同样需要数秒到数十秒。这也是 RDB 定位为「冷备 / 灾备 / 迁移」而非「实时保底」的原因。

#### 1.1.1 触发方式

| 方式 | 命令/配置 | 说明 |
| :-- | :-- | :-- |
| 手动保存 | `SAVE` | 主线程执行，阻塞所有命令，生产禁用 |
| 手动后台保存 | `BGSAVE` | fork 子进程执行，不阻塞主线程 |
| 自动保存 | `save 3600 1` 等 | 满足条件自动触发 BGSAVE |
| 关闭时 | `SHUTDOWN SAVE` | 正常关闭时自动触发 RDB |

**自动触发配置**：

```bash
save 3600 1      # 3600 秒内至少 1 次写操作
save 300 100     # 300 秒内至少 100 次写操作
save 60 10000   # 60 秒内至少 10000 次写操作
```

满足任意一个条件就触发一次 BGSAVE。如果要禁用 RDB：

```bash
save ""         # 禁用 RDB 自动触发
```

### 1.2 fork 与写时复制 {#fork-cow}

BGSAVE 的核心机制是 `fork` 与写时复制（Copy-On-Write，COW）。

#### 1.2.1 fork 子进程

`fork()` 创建子进程，子进程复制父进程的内存页表，得到一个「内存快照」。此时父子进程共享同一份内存，并不实际复制数据。

为什么必须 `fork` 出子进程来做，而不是主线程直接遍历内存写文件？Redis 主进程是单线程处理命令的：如果主线程直接序列化内存，那么在序列化期间（大内存实例可能持续数秒）所有客户端命令都会被阻塞，服务表现为整体卡死。`fork` 之后由子进程承担序列化与磁盘 IO，主进程继续响应命令，停顿只发生在 `fork` 调用本身那一瞬间。

```text
fork() 系统调用：
  1. 内核复制父进程的页表（不是内存数据）
  2. 子进程获得与父进程完全相同的虚拟地址空间
  3. 父子进程共享物理内存页（引用计数 +1）
  4. 子进程开始遍历数据，写 RDB 文件
```

#### 1.2.2 写时复制（COW）

子进程写 RDB 文件期间，如果主进程继续处理写命令修改了数据，操作系统会为被修改的内存页创建副本：

```text
fork 时刻：
  物理页 P1 → 被父子进程共享（引用计数=2）

主进程修改数据：
  1. 触发页错误（page fault）
  2. 内核为 P1 创建副本 P2
  3. 主进程写入 P2（新数据）
  4. 子进程继续读 P1（旧数据，快照一致性）
```

![fork 与写时复制](/redis/02-standalone-core-chapter-05-persistence-2.svg)

COW 同时带来两个收益：内存只复制被修改的页，而非整份数据；子进程读到的始终是 fork 时刻的旧数据，快照内容保持一致。代价是主进程每次写新页都要付出一次页复制的开销，写入越频繁、额外内存越多。

#### 1.2.3 fork 的代价 {#fork-cost}

| 项目 | 说明 |
| :-- | :-- |
| fork 耗时 | 取决于内存页表大小，具体值用 `latest_fork_usec` 实测，见 §2.4 |
| 内存开销 | 写入越多，COW 复制越多，极端情况内存接近翻倍 |
| 主线程阻塞 | fork 期间主线程短暂停顿，子进程写文件时不阻塞 |
| CPU 开销 | 子进程遍历数据生成 RDB 消耗 CPU |

> **生产环境最大坑**：实例内存越大，页表越大，`fork` 耗时越长，`fork` 期间主线程短暂停顿，可能导致客户端请求超时。解决方案是控制单实例内存规模，或用集群分片把数据分散到多个小实例。

> **另一个易忽略的坑：透明大页（THP）**。Linux 默认可能开启透明大页，`fork` 后触发 COW 时，内核以 2MB 大页为单位复制，而非 4KB 普通页。主进程哪怕只修改几个字节，也可能触发整页复制，导致 RDB 生成期间内存开销远大于实际写入量。Redis 官方文档建议在部署机器上关闭 THP（`echo never > /sys/kernel/mm/transparent_hugepage/enabled`）。

#### 1.2.4 查看 fork 耗时 {#fork-usec}

```bash
redis-cli INFO stats | grep latest_fork_usec
# latest_fork_usec:15234  （fork 耗时 15ms）
```

下表阈值为社区经验参考，非官方硬性标准，应结合自身 SLA 与实测基线调整：

| fork 耗时 | 评估 |
| :-- | :-- |
| < 10ms | 健康 |
| 10~100ms | 可接受 |
| > 100ms | 需要关注，可能导致请求超时 |
| > 1s | 严重问题，需拆分数据或优化 |

### 1.3 RDB 文件结构

RDB 文件是一个自描述的二进制文件：

```text
┌──────────────────────────────────────────┐
│ REDIS + 版本号                            │
├──────────────────────────────────────────┤
│ 辅助字段（redis-ver, ctime, used-mem 等）  │
├──────────────────────────────────────────┤
│ 数据库 0                                  │
│   ├── SELECTDB + db 编号                  │
│   ├── EXPIRETIME / EXPIRETIME_MS         │
│   ├── 类型 + key + value                  │
│   └── ...                                │
├──────────────────────────────────────────┤
│ 数据库 1 ...                              │
├──────────────────────────────────────────┤
│ EOF                                      │
├──────────────────────────────────────────┤
│ 校验和（CRC64）                            │
└──────────────────────────────────────────┘
```

### 1.4 配置详解

```bash
# 文件配置
dbfilename dump.rdb          # RDB 文件名
dir /var/lib/redis           # 文件保存目录
rdbcompression yes           # LZF 压缩（减少文件体积，消耗少量 CPU）
rdbchecksum yes              # CRC64 校验（检测文件损坏）
rdb-save-incremental-fsync yes  # 增量 fsync（减少写入峰值）

# 触发配置
save 3600 1
save 300 100
save 60 10000
```

| 配置 | 建议 |
| :-- | :-- |
| `rdbcompression` | 保持开启，LZF 压缩率高、CPU 开销低 |
| `rdbchecksum` | 保持开启，检测文件损坏 |
| `rdb-save-incremental-fsync` | 大 RDB 文件时建议开启，避免一次性 fsync 卡顿 |
| `save` | 根据数据重要程度调整频率 |

### 1.5 优缺点

| 维度 | 说明 |
| :-- | :-- |
| 优点 | 文件紧凑，二进制格式，加载恢复快（适合灾备） |
| 优点 | fork 子进程生成，主进程不阻塞（BGSAVE） |
| 优点 | 适合全量备份、跨机房迁移 |
| 缺点 | 快照之间宕机会丢失最后一段数据（不实时） |
| 缺点 | fork 大内存实例时有停顿风险 |
| 缺点 | 数据量大时 RDB 文件生成慢 |

## 2. AOF

### 2.1 原理 {#aof-principle}

AOF（Append Only File）记录服务器收到的每一条写命令，重启时按顺序重新执行这些命令来重建数据。

![AOF 追加流程](/redis/02-standalone-core-chapter-05-persistence-3.svg)

#### 2.1.1 写入流程

```text
客户端写命令 → 命令执行 → 追加到 AOF 缓冲区（aof_buf）→ 根据策略刷盘
```

关键点：写命令不是直接写磁盘，而是先写入内存中的 AOF 缓冲区，再根据 `appendfsync` 策略决定何时刷盘。

#### 2.1.2 三种刷盘策略

| 策略 | 配置值 | 刷盘时机 | 数据安全 | 性能 |
| :-- | :-- | :-- | :-- | :-- |
| 每次刷盘 | `always` | 每条命令都 `fsync` 到磁盘 | 最高，最多丢 1 条 | 最差 |
| 每秒刷盘 | `everysec` | 每秒 `fsync` 一次 | 较高，最多丢 1 秒 | 较好 |
| 不主动刷盘 | `no` | 交给操作系统（`write` 后不 `fsync`） | 最差，丢多少不可控 | 最好 |

```bash
appendfsync everysec   # 生产推荐
```

要理解三者的差异，先分清 `write` 与 `fsync` 是两层操作：

- `write()`：把命令从用户态缓冲区复制到**内核页缓存（page cache）**，此时数据仍在内存中、尚未落盘，断电即丢。
- `fsync()`：把内核页缓存真正刷写到磁盘，完成后数据才算持久化。

三种策略的底层差异：

```text
always:  write() → fsync() → 返回（每条命令都同步到磁盘）
everysec: write() → 返回（先写内核缓冲区）→ 后台线程每秒 fsync()
no:       write() → 返回（完全交给操作系统调度 fsync）
```

`everysec` 是 `write` 后立即返回（数据进内核页缓存，进程无需等磁盘），由后台线程每秒执行一次 `fsync`。两次 `fsync` 之间积累的命令若遇宕机，这部分未刷盘的命令会丢失——最多是 1 秒内的写入量，即「最多丢 1 秒」的由来。

> 生产环境默认推荐 `everysec`：性能损失小，最多丢失 1 秒数据，是安全与性能的最佳平衡点。`always` 会严重拖慢写入性能，只在极端一致性要求下使用。

### 2.2 重写

AOF 文件会随着写命令累积越来越大，需要定期「重写」压缩。

#### 2.2.1 为什么要重写

很多命令是冗余的，重写可以把「过程」压缩成「结果」：

```text
重写前：SET a 1; SET a 2; SET a 3; INCR a
重写后：SET a 4        ← 只保留最终结果
```

重写不是分析旧 AOF 文件，而是**读取当前内存数据**，生成一个只包含最终状态的最小命令集。

#### 2.2.2 重写原理

![AOF 重写流程](/redis/02-standalone-core-chapter-05-persistence-4.svg)

```text
1. 主进程 fork 子进程
2. 子进程遍历内存数据，生成新 AOF 文件
3. 子进程重写期间，主进程的新写命令追加到：
   - 旧 AOF 文件（保证旧文件完整）
   - AOF 重写缓冲区（aof_rewrite_buf）
4. 子进程重写完成，主进程把重写缓冲区追加到新文件
5. 原子替换旧文件
```

关键点：

| 环节 | 说明 |
| :-- | :-- |
| 子进程重写 | fork 子进程后台生成新文件，主进程不阻塞 |
| 增量缓冲 | 重写期间的新写命令记入重写缓冲区，最后追加到新文件 |
| 原子替换 | 新文件写完后 `rename` 原子替换旧文件 |
| fork 代价 | 与 RDB 的 fork 相同，大内存实例有停顿风险 |

#### 2.2.3 触发重写

```bash
auto-aof-rewrite-percentage 100   # AOF 增长超过 100% 触发
auto-aof-rewrite-min-size 64mb    # 最小触发体积（AOF < 64mb 不触发重写）
```

手动触发：

```bash
BGREWRITEAOF
```

### 2.3 文件损坏修复 {#aof-repair}

AOF 文件可能因为宕机、磁盘故障等原因损坏。Redis 提供了修复工具：

```bash
redis-check-aof --fix appendonly.aof
```

修复原理：扫描 AOF 文件，找到第一个格式错误的位置，截断其后的所有内容。

> 修复会丢失损坏点之后的数据。修复前建议先备份原文件。

## 3. 混合持久化

Redis 4.0 引入混合持久化：AOF 重写时，文件开头是 RDB 快照，之后追加增量 AOF 命令。

```text
混合持久化文件结构
┌─────────────────┬──────────────────────┐
│  RDB 快照头部    │  后续增量 AOF 命令     │
│  （快速恢复）     │  （实时性）           │
└─────────────────┴──────────────────────┘
```

恢复时先加载 RDB 部分（快），再重放 AOF 部分（保证最新数据）。

| 特性 | RDB | AOF | 混合 |
| :-- | :-- | :-- | :-- |
| 恢复速度 | 快 | 慢（重放命令） | 快（先加载 RDB） |
| 数据安全 | 丢快照间隔 | 最多丢 1 秒 | 最多丢 1 秒 |
| 文件体积 | 小 | 大 | 中等 |

```bash
aof-use-rdb-preamble yes   # 开启混合持久化（4.0+ 默认开启）
```

## 4. RDB vs AOF

| 维度 | RDB | AOF |
| :-- | :-- | :-- |
| 数据安全 | 丢失快照间隔的数据 | 最多丢失 1 秒（everysec） |
| 恢复速度 | 快（直接加载二进制） | 慢（重放命令） |
| 文件体积 | 小（二进制 + 压缩） | 大（文本命令） |
| fork 开销 | 每次快照都要 fork | AOF 重写也要 fork |
| 适用场景 | 灾备恢复、数据迁移 | 数据完整性优先 |

生产建议：两者同时开启，RDB 做冷备，AOF 做实时保底。Redis 恢复时优先用 AOF（数据更新）。

## 5. 持久化选型

| 场景 | 推荐方案 |
| :-- | :-- |
| 缓存（可丢数据） | 不开启持久化 |
| 数据重要、可容忍少量丢失 | 混合持久化 + `everysec` |
| 数据极重要、不能丢 | AOF `always` + 从库（性能代价大） |
| 灾备恢复 | RDB 定期备份 + AOF 实时保底 |

### 5.1 常见坑

| 坑 | 说明 |
| :-- | :-- |
| 主节点不开持久化 | 主从切换时新主无数据，数据丢失 |
| 只靠从节点持久化 | 主节点宕机数据全丢，从节点可能也没同步到 |
| 恢复优先级混乱 | 同时存在 RDB 和 AOF 时，Redis 优先用 AOF 恢复 |
| fsync 设置过严 | `always` 严重拖慢性能，非强一致需求别用 |

> 一个高频故障：主节点关闭持久化、依赖从节点持久化，主节点宕机后哨兵把从节点提升为主，但数据其实不全。正确做法是**主节点必须开启持久化**。
