# RDB 持久化

> Redis 的数据都在内存里，一旦宕机就全部丢失。RDB（Redis DataBase）通过「快照」把某个时间点的内存数据写到磁盘，实现持久化。本章讲解 RDB 的工作原理、触发方式与优缺点。

## 1. 工作原理

RDB 把某个时刻的内存数据整体序列化成一个二进制文件（默认 `dump.rdb`），恢复时直接把这个文件加载回内存。

![RDB 快照与恢复](/redis/02-standalone-core-chapter-03-rdb-1.svg)

### 1.1 触发方式

| 方式 | 命令/配置 | 说明 |
| :-- | :-- | :-- |
| 手动保存 | `SAVE` | 主线程执行，阻塞所有命令 |
| 手动后台保存 | `BGSAVE` | fork 子进程执行，不阻塞主线程 |
| 自动保存 | `save 900 1` 等 | 满足条件自动触发 BGSAVE |

**自动触发配置**：

```bash
save 900 1      # 900 秒内至少 1 次写操作
save 300 10     # 300 秒内至少 10 次写操作
save 60 10000   # 60 秒内至少 10000 次写操作
```

满足任意一个条件就触发一次 BGSAVE。

> `SAVE` 会阻塞主线程，生产环境禁用；`BGSAVE` 通过 fork 子进程后台完成，生产环境使用 `BGSAVE` 或自动触发。

## 2. fork 与写时复制

BGSAVE 的核心机制是 `fork` 与写时复制（Copy-On-Write，COW）。

### 2.1 fork 子进程

`fork` 让子进程复制父进程的内存页表，得到一个「内存快照」。此时父子进程共享同一份内存，并不实际复制数据。

### 2.2 写时复制

子进程开始写 RDB 文件后，如果主进程继续处理写命令修改了数据，操作系统会为被修改的内存页创建副本，子进程继续读旧数据，主进程改新数据。

![fork 与写时复制](/redis/02-standalone-core-chapter-03-rdb-2.svg)

关键点：

| 概念 | 说明 |
| :-- | :-- |
| fork 瞬间 | 复制页表，速度快，但大内存下仍有短暂停顿 |
| 写时复制 | 只复制被修改的页，不整体复制内存 |
| 内存开销 | 修改越多，额外内存越多；极端情况接近翻倍 |
| 大内存风险 | 内存很大时 fork 可能造成毫秒级到秒级的停顿 |

> fork 停顿是 RDB 的主要副作用。内存越大、fork 越慢，可能造成短暂的服务延迟。这也是大内存实例需要关注的性能点（见第五卷）。

## 3. 配置与优缺点

### 3.1 常用配置

```bash
dbfilename dump.rdb         # RDB 文件名
dir /var/lib/redis          # 文件保存目录
rdbcompression yes          # 是否压缩（LZF 算法）
save 900 1                  # 自动保存策略
```

### 3.2 优缺点

| 维度 | 说明 |
| :-- | :-- |
| 优点 | 文件紧凑、二进制格式加载快（适合灾备恢复） |
| 优点 | fork 子进程生成，主进程不阻塞（BGSAVE） |
| 缺点 | 快照之间宕机会丢失最后一段数据（不实时） |
| 缺点 | fork 大内存实例时有停顿风险 |

### 3.3 RDB 与 AOF 的选择

RDB 适合「允许少量数据丢失、看重恢复速度」的场景；AOF 适合「数据完整性优先、可容忍稍慢恢复」的场景。实际生产常用两者结合（混合持久化），见第 4 章。
