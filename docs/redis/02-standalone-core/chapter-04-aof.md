# AOF 与混合持久化

> AOF（Append Only File）通过记录每一条写命令来实现持久化，比 RDB 更接近「实时」。本章讲解 AOF 的原理、重写机制，以及 RDB + AOF 的混合持久化方案。

## 1. AOF 原理

AOF 记录服务器收到的每一条写命令，重启时按顺序重新执行这些命令来重建数据。

![AOF 追加流程](/redis/02-standalone-core-chapter-04-aof-1.svg)

### 1.1 三种刷盘策略

刷盘策略由 `appendfsync` 配置决定，权衡「性能」与「数据安全」：

| 策略 | 配置值 | 刷盘时机 | 数据安全 | 性能 |
| :-- | :-- | :-- | :-- | :-- |
| 每次刷盘 | `always` | 每条命令都同步到磁盘 | 最高，最多丢 1 条 | 最差 |
| 每秒刷盘 | `everysec` | 每秒同步一次 | 较高，最多丢 1 秒 | 较好 |
| 不主动刷盘 | `no` | 交给操作系统 | 最差，丢多少不可控 | 最好 |

> 生产环境默认推荐 `everysec`：性能损失小，最多丢失 1 秒数据，是安全与性能的最佳平衡点。

### 1.2 数据还原流程

重启时 Redis 按顺序重放 AOF 文件中的命令：

```text
AOF 文件：SET a 1 → SET b 2 → INCR a → DEL b
重放结果：a=2，b 不存在（按命令顺序执行）
```

## 2. AOF 重写

AOF 文件会随着写命令累积越来越大，需要定期「重写」压缩。

### 2.1 为什么要重写

很多命令是冗余的（先 SET 再 DEL，最终这个 key 不存在），重写可以把「过程」压缩成「结果」，大幅减小文件体积：

```text
重写前：SET a 1; SET a 2; SET a 3; INCR a
重写后：SET a 4        ← 只保留最终结果
```

### 2.2 重写原理

重写不是分析旧 AOF 文件，而是**读取当前内存数据**，生成一个只包含最终状态的最小命令集。

![AOF 重写流程](/redis/02-standalone-core-chapter-04-aof-2.svg)

关键点：

| 环节 | 说明 |
| :-- | :-- |
| 子进程重写 | fork 子进程后台生成新文件，主进程不阻塞 |
| 增量缓冲 | 重写期间的新写命令记入缓冲区，最后追加到新文件 |
| 原子替换 | 新文件写完后原子替换旧文件 |

### 2.3 触发重写

```bash
auto-aof-rewrite-percentage 100   # AOF 增长超过 100% 触发
auto-aof-rewrite-min-size 64mb    # 最小触发体积
```

## 3. 混合持久化

Redis 4.0 引入混合持久化：AOF 重写时，文件开头是 RDB 快照，之后追加增量 AOF 命令。

```text
混合持久化文件结构
┌─────────────────┬──────────────────────┐
│  RDB 快照头部    │  后续增量 AOF 命令     │
│  （快速恢复）     │  （实时性）           │
└─────────────────┴──────────────────────┘
```

混合持久化结合了两者优势：

| 特性 | RDB | AOF | 混合 |
| :-- | :-- | :-- | :-- |
| 恢复速度 | 快 | 慢（重放命令） | 快（先加载 RDB） |
| 数据安全 | 丢快照间隔 | 最多丢 1 秒 | 最多丢 1 秒 |
| 文件体积 | 小 | 大 | 中等 |

```bash
aof-use-rdb-preamble yes   # 开启混合持久化（4.0+ 默认）
```

## 4. 持久化选型与坑

### 4.1 选型建议

| 场景 | 推荐方案 |
| :-- | :-- |
| 缓存（可丢数据） | 不开启持久化 |
| 数据重要、可容忍少量丢失 | 混合持久化（`everysec`） |
| 数据极重要、不能丢 | AOF `always` + 从库 |

### 4.2 常见坑

| 坑 | 说明 |
| :-- | :-- |
| 主节点不开启持久化 | 主从切换时新主无数据，导致数据丢失 |
| 从节点开启持久化代替主节点 | 主节点宕机数据全丢，从节点可能也没同步到 |
| 恢复优先级混乱 | 同时存在 RDB 和 AOF 时，Redis 优先用 AOF 恢复（数据更新） |
| fsync 设置过严 | `always` 严重拖慢性能，非强一致需求别用 |

> 一个高频故障：主节点关闭持久化、依赖从节点持久化，主节点宕机后哨兵把从节点提升为主，但数据其实不全。正确做法是**主节点必须开启持久化**。
