# AOF 与混合持久化

> AOF（Append Only File）通过记录每一条写命令来实现持久化，比 RDB 更接近「实时」。本章讲解 AOF 的原理、重写机制、fsync 策略，以及 RDB + AOF 的混合持久化方案。

## 1. AOF 原理 {#aof-principle}

AOF 记录服务器收到的每一条写命令，重启时按顺序重新执行这些命令来重建数据。

![AOF 追加流程](/redis/02-standalone-core-chapter-04-aof-1.svg)

### 1.1 写入流程

```text
客户端写命令 → 命令执行 → 追加到 AOF 缓冲区（aof_buf）→ 根据策略刷盘
```

关键点：写命令不是直接写磁盘，而是先写入内存中的 AOF 缓冲区，再根据 `appendfsync` 策略决定何时刷盘。

### 1.2 三种刷盘策略

| 策略 | 配置值 | 刷盘时机 | 数据安全 | 性能 |
| :-- | :-- | :-- | :-- | :-- |
| 每次刷盘 | `always` | 每条命令都 `fsync` 到磁盘 | 最高，最多丢 1 条 | 最差 |
| 每秒刷盘 | `everysec` | 每秒 `fsync` 一次 | 较高，最多丢 1 秒 | 较好 |
| 不主动刷盘 | `no` | 交给操作系统（`write` 后不 `fsync`） | 最差，丢多少不可控 | 最好 |

```bash
appendfsync everysec   # 生产推荐
```

要理解三者的差异，先分清 `write` 与 `fsync` 是两层操作：

- `write()`：把命令从用户态缓冲区复制到**内核页缓存（page cache）**，此时数据仍在内存中、尚未落盘，断电即丢。
- `fsync()`：把内核页缓存真正刷写到磁盘，完成后数据才算持久化。

三种策略的底层差异：

```text
always:  write() → fsync() → 返回（每条命令都同步到磁盘）
everysec: write() → 返回（先写内核缓冲区）→ 后台线程每秒 fsync()
no:       write() → 返回（完全交给操作系统调度 fsync）
```

`everysec` 是 `write` 后立即返回（数据进内核页缓存，进程无需等磁盘），由后台线程每秒执行一次 `fsync`。两次 `fsync` 之间积累的命令若遇宕机，这部分未刷盘的命令会丢失——最多是 1 秒内的写入量，即「最多丢 1 秒」的由来。

> 生产环境默认推荐 `everysec`：性能损失小，最多丢失 1 秒数据，是安全与性能的最佳平衡点。`always` 会严重拖慢写入性能，只在极端一致性要求下使用。

## 2. AOF 重写

AOF 文件会随着写命令累积越来越大，需要定期「重写」压缩。

### 2.1 为什么要重写

很多命令是冗余的，重写可以把「过程」压缩成「结果」：

```text
重写前：SET a 1; SET a 2; SET a 3; INCR a
重写后：SET a 4        ← 只保留最终结果
```

重写不是分析旧 AOF 文件，而是**读取当前内存数据**，生成一个只包含最终状态的最小命令集。

### 2.2 重写原理

![AOF 重写流程](/redis/02-standalone-core-chapter-04-aof-2.svg)

```text
1. 主进程 fork 子进程
2. 子进程遍历内存数据，生成新 AOF 文件
3. 子进程重写期间，主进程的新写命令追加到：
   - 旧 AOF 文件（保证旧文件完整）
   - AOF 重写缓冲区（aof_rewrite_buf）
4. 子进程重写完成，主进程把重写缓冲区追加到新文件
5. 原子替换旧文件
```

关键点：

| 环节 | 说明 |
| :-- | :-- |
| 子进程重写 | fork 子进程后台生成新文件，主进程不阻塞 |
| 增量缓冲 | 重写期间的新写命令记入重写缓冲区，最后追加到新文件 |
| 原子替换 | 新文件写完后 `rename` 原子替换旧文件 |
| fork 代价 | 与 RDB 的 fork 相同，大内存实例有停顿风险 |

### 2.3 触发重写

```bash
auto-aof-rewrite-percentage 100   # AOF 增长超过 100% 触发
auto-aof-rewrite-min-size 64mb    # 最小触发体积（AOF < 64mb 不触发重写）
```

手动触发：

```bash
BGREWRITEAOF
```

## 3. 混合持久化

Redis 4.0 引入混合持久化：AOF 重写时，文件开头是 RDB 快照，之后追加增量 AOF 命令。

```text
混合持久化文件结构
┌─────────────────┬──────────────────────┐
│  RDB 快照头部    │  后续增量 AOF 命令     │
│  （快速恢复）     │  （实时性）           │
└─────────────────┴──────────────────────┘
```

恢复时先加载 RDB 部分（快），再重放 AOF 部分（保证最新数据）。

| 特性 | RDB | AOF | 混合 |
| :-- | :-- | :-- | :-- |
| 恢复速度 | 快 | 慢（重放命令） | 快（先加载 RDB） |
| 数据安全 | 丢快照间隔 | 最多丢 1 秒 | 最多丢 1 秒 |
| 文件体积 | 小 | 大 | 中等 |

```bash
aof-use-rdb-preamble yes   # 开启混合持久化（4.0+ 默认开启）
```

## 4. AOF 文件损坏修复 {#aof-repair}

AOF 文件可能因为宕机、磁盘故障等原因损坏。Redis 提供了修复工具：

```bash
redis-check-aof --fix appendonly.aof
```

修复原理：扫描 AOF 文件，找到第一个格式错误的位置，截断其后的所有内容。

> 修复会丢失损坏点之后的数据。修复前建议先备份原文件。

## 5. 持久化选型

| 场景 | 推荐方案 |
| :-- | :-- |
| 缓存（可丢数据） | 不开启持久化 |
| 数据重要、可容忍少量丢失 | 混合持久化 + `everysec` |
| 数据极重要、不能丢 | AOF `always` + 从库（性能代价大） |
| 灾备恢复 | RDB 定期备份 + AOF 实时保底 |

### 5.1 常见坑

| 坑 | 说明 |
| :-- | :-- |
| 主节点不开持久化 | 主从切换时新主无数据，数据丢失 |
| 只靠从节点持久化 | 主节点宕机数据全丢，从节点可能也没同步到 |
| 恢复优先级混乱 | 同时存在 RDB 和 AOF 时，Redis 优先用 AOF 恢复 |
| fsync 设置过严 | `always` 严重拖慢性能，非强一致需求别用 |

> 一个高频故障：主节点关闭持久化、依赖从节点持久化，主节点宕机后哨兵把从节点提升为主，但数据其实不全。正确做法是**主节点必须开启持久化**。
