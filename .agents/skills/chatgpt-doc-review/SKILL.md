# ChatGPT 技术文档迭代评审

用 ChatGPT 做文档的诊断器和反方，但不把它当作定稿者。先发现问题，再判断取舍，通过复查和对质收敛分歧，最终由 agent 根据证据决定如何修改。

cdr 负责机械操作，包括文档路由、发送 prompt、等待生成和抓取回复；agent 负责技术判断、意见取舍和修改落地。所有浏览器操作一律通过 cdr 命令完成，不手写 Playwright 选择器。

## 责任划分

| 角色 | 职责 | 对应环节 |
|------|------|---------|
| cdr（机械层） | 文档路由、组装 prompt、发送、等待生成、抓取回复 | route / send |
| ChatGPT（反方） | 诊断、复核取舍、复查、对质 | 4 次交互 |
| agent（判断层） | 技术判断、意见取舍、修改落地 | 分析落地（不调用 ChatGPT） |

「ChatGPT 交互轮次」连续 1~4：1 问诊、2 分析复核、3 复查、4 对质。其中 round 1 由 `cdr review` 一步完成（路由判断 + 新开对话发送），round 2/3/4 通过 `cdr send --round` 使用内置模板。

## 触发场景

- 用户要求把技术文档交给 ChatGPT 评审或打磨。
- 用户要求根据 ChatGPT 的意见修改技术文档。
- 用户要求复核已有评审意见、检查修改效果或针对分歧继续对质。
- 用户要求对多篇文档复用这套迭代流程。

用户只需要一次性技术问答或简单评审意见时，不必启动完整流程。用户明确指定使用 Gemini 时，改用对应约定。

## 前置检查

1. 明确评审对象：给出文档的本地绝对路径即可。repo、分支、仓库内相对路径均由 cdr route 根据文件路径自动检测，无需手动提供。
2. 超过 80 个字符的命令，或使用 python 代码时，一律写成临时脚本再执行。临时脚本必须放在 workspace 的 `.cache/` 目录下，临时脚本文件名要按照 `.cdr_round2_<诊断文件名>_<时间戳>` 的格式，防止多个评审流程并发时重名覆盖。执行后删除临时脚本，避免污染 Git 工作区。

## 工作流

问诊 → 分析复核 → 分析落地 → 复查 → 对质 → 定稿。

1. cdr review --file <文档绝对路径> --json
2. cdr send --round 2 --adopt "<采纳项>" --converge "<收敛项>" --reserve "<保留项及理由>" --url "<第一轮返回的 url>" --tab "<第一轮返回的 tab_id>" --keep-tab --json
3. agent 根据前两轮结果修改文档
4. cdr send --round 3 --file "<修改后文档路径>" --url "<第一轮返回的 url>" --tab "<第一轮返回的 tab_id>" --keep-tab --json
5. cdr send --round 4 --dispute "<争议段落>" --accepted "<已接受的批评>" --reserve-reason "<保留理由>" --url "<第一轮返回的 url>" --tab "<第一轮返回的 tab_id>" --close-tab --json

各阶段各有独立目标，不为了走完流程而机械执行，也不无限迭代。

### 阶段 1 · 问诊（ChatGPT 交互 1）

目标：获得覆盖技术准确性、结构、清晰度和去 AI 味四个维度的诊断意见。

使用 cdr review 一步完成路由判断与发送（脚本内部自动检测 repo/分支/路径、判断送审方式并新开对话发送）。

命令示例：

cdr review --file <文档绝对路径> --json

该项目评审统一使用 --project the-stack。第一轮 cdr review 固定新开对话并保留该 tab（--keep-tab）。记录返回 JSON 中的 url 作为对话锚点、tab_id 作为 tab 锚点（后续轮次复用同一 tab）；检查 conversation_id / url 确认进入正确的 ChatGPT 项目。the-stack 对应的 GPT ID 为 g-p-6a722a3bb3f0819194bd49c108946e51。

cdr review 会等待生成结束并抓取回复。拿到诊断后，先核对评审对象和版本是否正确，再进入分析复核阶段。

### 阶段 2 · 分析复核（ChatGPT 交互 2）

目标：让 ChatGPT 复核 agent 对第一轮意见的取舍，而不是直接生成改写稿。

先将第一轮意见分为三类：

- 采纳：有明确依据，准备修改。
- 收敛：方向合理，但需要缩小修改范围或调整表达。
- 保留：暂不采纳，并记录具体理由。

将分类结果和保留理由填入第二轮模板，重点询问：

1. 是否存在被误判为正确、实际上不应修改的意见？
2. 是否存在被保留、实际上确实需要修改的问题？
3. 对保留意见的理由是否成立？如果不成立，具体原因是什么？

执行（使用第一轮返回的 URL 续接）：

cdr send --round 2 --adopt "<采纳项>" --converge "<收敛项>" --reserve "<保留项及理由>" --url "<第一轮返回的 url>" --tab "<第一轮返回的 tab_id>" --keep-tab --json

本轮只复核取舍，不要求 ChatGPT 提供改写稿。收到回复后，由 agent 独立判断，不因 ChatGPT 坚持某项意见就自动改变决定。

### 阶段 3 · 落地复查（ChatGPT 交互 3）

目标：根据前两轮的诊断和复核结果，决定实际修改范围，执行修改，并检查修改是否真正解决了问题，以及修改过程中是否引入了新问题。

技术准确性问题优先处理，但必须核实事实依据。涉及框架版本、API 行为、源码实现或概念边界时，必要时查阅对应版本的官方文档或源码。证据不足时标记待核实，不把 ChatGPT 的判断直接当成结论。

结构建议需要结合段落功能判断。删减、合并或调整章节之前，先确认是否会造成解释缺口；可以局部调整时，不必重构整篇文档。

风格建议只采纳有明确收益的部分。去 AI 味不是机械地缩短句子、改变句式或消除所有结构对称，而是减少空泛总结、套路化过渡、重复解释和不必要的铺陈。

核心原则：每项改动都应有明确理由。ChatGPT 建议删除某段时，先判断它承担什么解释任务、删除后是否造成信息缺口，以及是否存在更简洁的替代方案。既不因它坚持删除就妥协，也不因它坚持删除就一概保留。

修改时只处理已确认的问题，不顺手重构无关内容。完成后保留修改后的完整文档，进入复查阶段。

使用第一轮返回的 URL 续接，使 ChatGPT 能结合前序诊断和复核意见检查修改结果。

执行（使用第一轮返回的 URL 续接，cdr 自动附带复查问题并拼接修改后的文档）：

cdr send --round 3 --file "<修改后文档路径>" --url "<第一轮返回的 url>" --tab "<第一轮返回的 tab_id>" --keep-tab --json

复查重点：

1. 前几轮确认的问题是否已经解决，是否仍有遗漏或修正不彻底的地方？
2. 已保留的内容是否确实存在技术错误或其他必须修改的问题？
3. 修改后的文档是否出现新的技术错误、表达歧义或结构问题？

对复查结果逐项核实，不把单纯的风格偏好当作必须修改的问题。没有发现新问题时，可以直接进入定稿；存在重要分歧时，进入对质分歧阶段。

### 阶段 4 · 对质分歧（ChatGPT 交互 4）

目标：针对 agent 与 ChatGPT 的具体分歧，要求其明确说明依据并给出可执行的结论。

执行（使用第一轮返回的 URL 续接，与前面各轮同一对话）：

cdr send --round 4 --dispute "<争议段落>" --accepted "<已接受的批评>" --reserve-reason "<保留理由>" --url "<第一轮返回的 url>" --tab "<第一轮返回的 tab_id>" --close-tab --json

要求 ChatGPT 逐项明确表态：是否撤回原建议；如果仍坚持，依据是什么；如有必要，给出最小修改措辞。

对质的目的是查明事实和推理，不是争赢。ChatGPT 承认误判可以结束该项争论，但最终仍应依据事实和文档实际效果判断，而不是把它的认错当作唯一依据。

证据不足或分歧无法解决时，明确记录待核实事项，不强行定稿。

## 定稿原则

1. ChatGPT 的改写稿不能直接照搬。它可能把一句话扩展成多段，或引入新的套路化表达。只提取必要信息，做最小修正。
2. 宁少勿多。只修改已确认的问题，不顺手重构全文，也不为了去 AI 味而刻意改变自然表达。
3. 每项改动都应有明确的技术、结构或表达依据。无法说明收益的修改不做。
4. 不把 ChatGPT 的意见当成权威。技术事实以可核实的文档、源码和实际行为为准。
5. 分歧逐项收敛，解决后不再无故扩展修改范围。
6. 流程服务于文档质量，而不是反过来。没有必要时不强行进入下一轮；问题尚未核实时不因轮次结束而强行定稿。
7. 最终定稿权属于用户。agent 应说明重要取舍及仍待核实的问题，不擅自把争议意见当成用户已经认可的结论。

## 对话续接规则（硬约束）

**同一对话是评审能生效的前提，必须全程续接，绝不中断。**

整个评审流程只新建一次对话（问诊阶段），之后每次 ChatGPT 交互都必须显式用 --url 续接同一个对话；不允许省略 --url 依赖默认定位，更不允许重新 --new-chat（那会另开新对话、丢掉前序评审记忆）。

可靠的做法是：

1. 问诊阶段使用 --new-chat 新建对话。
2. 保存问诊阶段 cdr review 返回的 url（对话锚点）和 tab_id（tab 锚点），整个评审复用同一个 tab。
3. 后续每次交互（分析复核、复查、对质）都必须带 --url 与 --tab 续接同一对话、同一 tab；中间轮（round 2/3）加 --keep-tab 保留，最后一轮（round 4）加 --close-tab 关闭。
4. 「分析落地」阶段不调用 ChatGPT、不发 prompt，对话保持不变；之后的「复查」继续用问诊阶段的 url，不要因为隔了 agent 环节就重新新建。
5. 不要为了续接上下文重新使用 --new-chat，否则会丢失前序评审记忆。
6. 只有开始一个独立文档或独立子目录的评审时，才新建对话。

cdr 在每次 `cdr send --url` 成功后会自动校验返回的 conversation_id 与 --url 锚点一致；一旦串到其他对话，会报错并阻断（不返回该对话的回复），无需 agent 肉眼核对 URL。

tab 生命周期：问诊（cdr review）新建并保留一个 tab，之后各轮通过 --tab 复用同一个 tab（同一 url 多个 tab 时靠 target id 精确区分，不会串到别的 tab），最后一轮 --close-tab 关闭。整个流程只占用一个 tab，且不与并行的其他评审 tab 冲突。

## 长 prompt 与临时脚本

符合前置检查第 2 条阈值的命令一律写成 workspace 内的临时脚本再执行，避免长命令、引号、换行和特殊字符导致调用失败。

发送完整文档时，先检查 cdr 是否支持从文件读取 prompt。若支持，优先使用文件输入；若不支持，通过 workspace 内的临时脚本安全传递内容，不要假设存在未经确认的 CLI 参数。

## 异常处理

- cdr 未链接、cgpt 缺失或 Playwright 未安装：先修复依赖，再继续流程，不退回手写 Playwright 选择器。
- ChatGPT 未登录：提醒用户完成登录，确认登录态恢复后再继续。
- 发送后没有得到完整回复：检查 cdr 返回结果和当前对话状态，确认失败原因后再决定是否重试，避免重复发送。
- 续接到错误对话：cdr 会自动校验 conversation_id 并阻断，无需 agent 处理。
- 续接到错误项目：检查 URL 中的项目标识，确认进入正确的 ChatGPT 项目后重试。
- 技术事实缺乏依据：标记待核实，必要时查阅对应版本的官方文档或源码，不以多轮对话代替事实核验。

## cdr 命令参考

cdr 通过 PATH 中的软链接 ~/bin/cdr 调用。完整参数列表与说明以 `cdr --help`（或 `cdr <子命令> --help`）为准，这里只记录各命令的职责与调用时机。

- cdr route：只读路由。读取文档并决定送审方式、生成送审文本，不实际发送。需要单独查看送审文本时用。实际评审由 cdr review 一步完成，无需手动 route。
- cdr review：第一轮问诊一步完成（路由判断 + 新开对话发送），默认 --project the-stack，返回 JSON 含 url（对话锚点）与 tab_id（tab 锚点）。
- cdr send：发送 prompt 并抓取回复。用 --round 2|3|4 时加载 prompts/ 下对应模板并填充占位符，agent 只传判断结果、不手动拼 prompt。续接对话一律用 --url + --tab 锚点。

关键锚点：第一轮 cdr review 返回的 url 与 tab_id 是整个流程的续接依据。中间轮（round 2/3）加 --keep-tab 保留 tab，最后一轮（round 4）加 --close-tab 关闭。cdr 每次 send --url 成功后会自动校验 conversation_id 与锚点一致，串到其他对话会报错阻断。

模板存放在 cdr 脚本同目录的 prompts/ 下（round-1~4.md、github-read.md），需要调整大段 prompt 文案时直接编辑对应 .md 文件。
